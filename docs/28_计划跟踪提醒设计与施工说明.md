# 计划跟踪提醒设计与施工说明

日期：2026-11-07

状态：计划轮询已并入飞书 bot 进程；计划编号已改为 P 格式。2026-11-07 12:02 CST 重启后首轮检查 1 条活动计划，真实触发消息尚未验收。

## 1. 目标

用户明确要求跟踪一份交易计划后，由现有飞书 bot 进程内的共享轮询任务定时读取行情；条件触发后，任务把带来源标记的结构化事实提交给同一会话的 `ConversationService`，LLM 结合历史上下文生成回复，再经正常飞书投递链路发给用户。任务只检测确定条件，不替用户开单，也不让 LLM 每 15 分钟轮询行情。

这是“入场条件提醒”，不是模拟订单跟踪。用户确认已开仓后，可用现有模拟订单流程记录订单；但本 worker 不会周期检查 `paper_orders`，现有订单仍按行情请求触发兑单。计划提醒不能把目标价触及解释成用户已成交。

## 2. 复用与边界

- 行情复用 `tools.market_data.fetch_market_data`，不另建交易所客户端。
- 加密货币取 Gate.io 现货 K 线；股票/黄金沿用行情工具对应的 AKShare 数据。现货 K 线不代表永续合约标记价、盘口或成交价。
- 通知复用现有 `FeishuAdapter -> ConversationService -> NativeAgentLoop` 和 delivery 事件链路；原会话范围与接收地址从服务端 `ToolContext.conversation_scope` 保存，不允许 LLM 指定接收人。
- 监控计划复用 `journal_ideas` 的 `watch` 记录和 `meta_json`，不创建 `paper_orders`，不新增数据库表。
- `run_feishu_longconn` 在 bot 进程内启动一个 daemon 轮询线程；计划和进度仍持久化在数据库，不单独维护 worker 进程。
- 只支持明确的价格/收线条件。自然语言形态描述保留在 LLM 对话里；不能确定映射到哪条规则时先询问，不在后台调用 LLM 猜条件。

## 3. 首版触发规则

首版监控一种可复核的“进入区间后收回”信号，默认周期为 15m；用户明确指定时也支持 1h、4h。周期与前序行情分析周期无关。计划有效期默认 8 小时，可设为 1 到 72 小时：

- 做空：先前收线在入场区下方；后续某根已收线监控周期 K 线的高低区间与入场区相交，且该根或之后的收盘价低于区间下沿，触发一次提醒。
- 做多：先前收线在入场区上方；后续某根已收线监控周期 K 线的高低区间与入场区相交，且该根或之后的收盘价高于区间上沿，触发一次提醒。
- 计划到期后不再评估；行情请求失败时不把失败解释为“条件未触发”，下一轮继续尝试。
- K 线已触发但提醒一直发送失败、且计划已到期时，丢弃过期提醒并结束计划，不在过期后发送陈旧的入场信号。
- 消费已收线 K 线并按时间顺序检查，保存区间已触及状态，避免 worker 重启后重复触发旧 K 线。

触发时 worker 将标的、周期、规则、收盘时间和 OHLC 事实作为带有“后台监控事件，非用户原话”标记的会话输入并写入原会话。LLM 负责结合历史上下文解释并向用户回复；程序确认的触发事实不可被模型否认，回复须明确“不代表已成交或必须开仓”。之后用户追问时，模型能在同一历史里看到提醒和自己的回复。

每次 LLM 处理尝试使用独立的入站幂等键；失败会留下可见的中止记录，计划保持待通知并在后续轮询重试。原会话正在处理其他请求时，沿用会话锁并在后续轮询重试。成功回复沿用现有 delivery 幂等和不确定状态规则，避免 worker 重启后重复发送已完成的回复。模型服务持续失败时，提醒可能延迟到后续重试或计划到期。

OHLC 只能证明该根 K 线的价格范围与区间相交、以及收盘位置，不能证明 K 线内部价格先后路径或实际成交。

## 4. ETH 示例如何落地

原建议中的 2267–2282 是入场观察区；“进入后 15m 受阻并收回 2267 下方”可映射为首版做空规则。省略监控周期时使用 15m，省略有效期时使用 8 小时。3 天计划传入 72 小时，4h 计划传入 `interval=4h`。

2293 的 1h“重新站稳”仍需明确收线次数/规则，且首版不监控失效线。止损“2293 上方”不是具体止损价格。2253 和 2237.4 是入场后的止盈参考，不是入场触发价；首版入场提醒不监控止盈，也不推断用户已持仓。若用户要记录模拟持仓，可在开仓后另行创建模拟单；若要在后台周期检查该订单并推送止盈止损，还需后续扩展。

“冲高回落”“触底反弹”“横盘磨底”本身不作为后台规则。可由 LLM 在用户确认后转为已支持的收线条件；如果结构定义不完整，就先追问或只给普通行情建议，不启动监控。

## 5. 状态与失败处理

计划状态保存在 `journal_ideas.meta_json.plan_monitor`：`active`、`notice_pending`、`triggered`、`expired`、`cancelled`。对外计划编号为 `P` + `journal_ideas.id`，订单编号为 `T` + `paper_orders.id`，至少补零至 5 位；数据库自增 ID 是编号来源，不另维护计数器。周期和有效期分别保存在现有 `journal_ideas.interval`、`valid_until` 字段，不需要数据库迁移。每个新计划独立保存，不会自动替换同一会话的旧计划；旧计划继续跟踪，直到触发、到期或被明确取消。过期同步 `journal_ideas.state=expired`；触发后任务先保存待 LLM 处理状态，正常会话处理完成后再标记完成，失败则保留重试。市场数据失败只记日志并保留 active 状态，直到数据恢复或计划到期。bot 退出时轮询暂停，数据库中的计划保留并在 bot 重启后继续检查。

飞书私聊提醒发回原用户；群聊提醒发回原群。Web 会话没有当前可复用的主动推送通道，首版拒绝创建后台提醒。接收范围按原会话保存，群聊成员可能看到提醒内容。

## 6. 运行方式

飞书 bot 启动时会自动启动轮询任务，无需单独启动计划跟踪进程：

```bash
python runtime/cli/feishu_bot.py
```

bot 与轮询任务共享同一进程、运行配置、数据库和 FeishuAdapter。当前容器没有 systemd，bot 用 `setsid` 脱离 SSH 启动，日志位于 `/tmp/marketass_feishu_bot_light_history.log`。这能避免 SSH 断开时退出，但进程崩溃或主机重启后不会自动拉起；生产需配置 supervisor 或等价管理器。轮询任务每 15 分钟运行一次，仅评估计划所选周期已收盘的 K 线；提醒延迟可能接近一个轮询周期，不保证成交价或成交。

## 7. 首版验收

- 用户明确要求后，LLM 创建监控计划；没有明确授权或规则不完整时不创建。
- 做空计划仅在区间触及后出现指定收线条件才提醒；未触发、失效、到期和数据失败不混为一类。
- LLM 回复成功后沿用原会话投递与幂等记录；发送结果不确定时遵守现有 delivery 状态，不盲目重发。
- 计划创建不产生模拟订单；提醒本身不声称用户开仓。
- bot 重启后能够从持久化状态继续，不重放已完成提醒。

首版已实现创建、查询、取消、持久化轮询、会话内 LLM 通知、失败重试和到期处理；未实现 2293 失效线及 TP1/TP2 监控。bot 重启后的活动计划恢复能力已经由轮询入口接入；真实提醒投递仍需等待有效计划触发验收。
