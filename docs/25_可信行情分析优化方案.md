# 可信行情分析优化方案

日期：2026-10-15

状态：复盘提示词已实施；评分工具因真实样本未满足适用条件，暂未接入

依据：[21_行情事实与决策分层方案.md](21_行情事实与决策分层方案.md)、[24_可信行情分析报告.md](24_可信行情分析报告.md)

## 1. 目标与范围

行情分析是概率判断。长期目标是足够样本、固定规则、计入成本后的正期望，不是每次预测正确；高胜率本身也不保证盈利。允许判断错误、计划止损、证据不足，不用后续走势替旧建议补条件。

本轮只做两件事：收紧复盘表达；增加一个只读 `trusted_review` 工具，对明确的历史计划做有限、可重复的验证。

- 普通行情问答继续由 LLM 自主选工具、解释结构、提出交易假设，不增加固定工作流或强制计划模板。
- 历史复盘先引用旧原文，再使用代码计算结果；LLM 可以解释原因，不能改写结果。
- 只评价指定计划，不自动挑最近一条，也不根据一两个成功样本证明方法有效。
- 不新增数据库表、订单状态、长期记忆、依赖、通用抽取服务或回测框架。
- 暂不做历史盲测、关键位反应评分、策略统计和模型裁判服务。

工具能证明的是“原文里的明确价格，在公开的 OHLC 规则下出现了什么结果”，不是技术分析已经具备预测优势。

## 2. 当前调用链与改动边界

现有主链路保持不变：

```text
ConversationService -> 事件日志与上下文压缩 -> NativeAgentLoop -> ToolExecutor
```

普通行情仍使用 `analyze_market`、快照和情绪工具。可信复盘只是新增一种工具调用：

```text
search_session_history 找原文和 event_id
  -> trusted_review 校验原文、取后续 K 线、机械计算
  -> 原有 LLM 解释结果与局限
```

无需新增 router、多 agent 或额外模型调用。对“为什么亏”“当前是否继续持有”等讨论，也不强制套用复盘工具；只有判断旧计划的输赢、命中或方法有效性时才要求可验证证据。

| 现有能力 | 本轮用途与限制 |
| --- | --- |
| `ToolContext.conversation_scope / event_store` | 服务端授权域；工具不接受用户身份、路径或其他可见域参数 |
| `search_session_history` | 找候选原文；多条建议不能合成一条获胜计划 |
| `LocalSessionEventStore.scan_scope / resolve_event_payload` | 读取活动分支原始事件和完整 blob；摘要不是原文 |
| `HistoricalClaimGuard` | 继续检查历史引用；不能证明语义或收益正确 |
| `_fetch_crypto_kline / _http_get_json` | 复用 Gate 请求和行转换；目前只有最新数据，需要内部时间窗参数 |
| `analysis_snapshots` | 保持现状，不增加查询接口；不是交易计划真相源 |

## 3. 先修改提示词

归属 `src/core/prompt.py`，集中补充短规则，不改所有工具描述，不扩展 `position_review` 的持仓职责：

1. 行情观点使用概率和失效条件，不编造没有统计依据的胜率或信心百分比。
2. 评价旧建议必须取原文；旧回复没有写的条件只能作为新建议，不能倒灌回旧计划。
3. 止损算失败，未触发不算盈利，支撑跌破不能默认改判为“转压力所以原来有效”。
4. 没有工具层隔离未来上下文，就不能声称做过盲测；单次验证不能证明方法有效。
5. 工具返回失败或不可验证时明确说出来，随后可以解释或讨论，但不能补字段后冒充原计划。

同时替换现有 `level_zones_v1` 的“反复争夺”示例：`touches` 是候选聚集数量，不是独立触碰次数；`strength` 也不能直接当作历史命中率。只改提示词里的解释，不改计算、字段名、快照或中文展示协议。

提示词是表达约束，不是安全证明。验收要看模型实际回答，不写提示词字符串包含测试。

## 4. 工具的最小接口

`trusted_review(..., *, context: ToolContext)` 注册为 `pure_query`、`requires_context=True`。

输入为扁平参数，不引入嵌套模型：

```json
{
  "event_id": "ev_xxx",
  "plan_quote": "ETHUSDT 4h 做空；入场 2510；止损 2538；止盈 2474。",
  "symbol": "ETHUSDT",
  "interval": "4h"
}
```

四个参数必填。代码只读取原文里唯一、带标签的简单计划字段，缺失就返回 `unverifiable`，不再让 LLM 重复传一次价格和方向。工具不接受 `days`、用户身份、任意历史起止时间或可调评分规则；LLM 只定位证据，不负责评分。

第一版仅支持加密 USDT、`15m/1h/4h/1d`、单个明确入场价、触价止损和单个明确止盈价的普通限价计划。区间入场、多档止盈、突破单、收线止损、附加确认条件或有效期暂不计算完整输赢，直接说明未支持，不猜中点或默认仓位。

这是评分能力边界，不要求以后所有行情分析都按该格式写。原有模拟单的实际成交和盈亏仍由台账回答，不能用本工具冒充。

### 4.1 原文校验

先执行以下原文校验；失败不获取行情、不返回胜负。行情到齐后再做第 4.2 节的时间与路径校验：

1. 使用服务端 `conversation_scope` 调用 `scan_scope`，精确找 `event_id`。只接受活动分支的 `assistant/message`，且有文本建议；不能以用户转述、工具结果、模型请求或摘要代替。
2. 用 `resolve_event_payload` 取完整原文；`raw_content_unavailable=true` 时返回不可验证，不能对 blob 指针或截断预览评分。
3. 引文按行选择：起点为消息开头或换行之后，终点为换行之前或消息末尾；只归一行内空白和换行编码后做连续子串校验，不能拼接或裁掉同一行的后半句。支持多行列表，不要求整个段落符合固定模板。
4. 引文中只能有一个方向，以及各一项带 `入场/entry`、`止损/SL/stop`、`止盈/TP/target` 标签的单值价格；标签和值按明确位置对应，重复项、区间或残余价格表达均拒绝，不能只检查全文出现了相同数字。标的和周期可在消息标题中，但整条消息必须唯一且与输入一致，不默认周期、不猜哪个标的。
5. 检查整条消息而非只检查引文：存在条件性语句（例如若、如果、确认、收线、受阻、止跌、站稳、突破）、有效期或多个计划时，返回 `unverifiable`。全文方向词或任一种计划字段标签出现多项，也直接拒绝，不推断它们是否属于同一计划。不能为了让片段通过而忽略标题或前文的全局条件。局部校验不是通用语义证明，无法判定作用域的文案不评分；使用少量显式规则，不另调用 LLM 或构建通用解析器。
6. 检查价格有限且大于零；做多满足 `stop < entry < target`，做空相反。禁止把错配字段归一成合理计划。

使用 Python 标准库 `re` 和 `decimal.Decimal` 即可；数值允许等价小数，不改语义。匹配不能从 `2538` 中截取 `538`。原文条件识别仍有自然语言局限，工具只给有限规则下的价格路径核对，不能声称完成了所有语义验证。结果必须返回原始引文、解析出的字段和验证口径。

首版不用全局事件索引：一次工具调用扫描一次可见域、精确选一条事件，复杂度 O(E)。先复用现有读取方式；批量复盘或真实日志规模出现瓶颈后再考虑索引。

### 4.2 后续行情的时间边界

当前 `_fetch_crypto_kline` 默认只取最新 200 根，不能直接拿来验证任意历史计划。为它增加仅内部使用的 `start_time/end_time`，有时间窗时使用 Gate Spot `from/to`，不同时传 `limit`；普通调用及 LLM 的 `fetch_market_data` 接口保持不变。时间窗分支严格检查支持周期，不沿用静默回退 `1d`、最少 30 根、末尾切片和跳过坏行的最新行情逻辑。

- 来源固定为 Gate 现货，与当前加密行情分析一致；不是合约成交或账户回报。原文明确出现“合约/永续/futures/perpetual”时，只返回 `spot_proxy` 价格触及近似，不给合约计划胜负或 R。未明确市场时按现货价格做理论路径核对，不认定用户正在做现货或合约；其中 short 只是下跌方向的虚拟计划，不表示现货可直接做空。
- 起点使用助手事件的实际 `occurred_at`，不是 LLM 传入的时间。按交易所 UTC 网格读取发言所在 K 线以及接下来最多 24 根；只使用已完整收线的记录。
- 发言所在 K 线不能直接跳过：若该根触及入场价，无法知道触价在发言前还是之后，返回 `unverifiable`，不能假装后来仍未成交。若整根都未触及入场，才安全地从下一根开始评分。发言恰好在开线时刻时，从该根开始共评 24 根，不另加保护根。非开线时刻则最多读 1 根保护根加后续 24 根；`data_window.bars` 只计评分根。保护根尚未收完返回 `incomplete_window`，不凭尚在变化的 high/low 判定没有触发。
- 固定观察后续 24 根，此窗口是工具评分约定，不是旧计划有效期。一个有界请求最多读取 25 根，校验排序、去重、开收线边界、OHLC 有效性和连续性；不能用未收线数据，不退回最新数据。
- 明确触发终点后可以提前结算，不必等满 24 根；但从起点到该终点的证据必须连续完整。只有判定 `untriggered/unresolved` 才要求完整 24 根；未满窗口无终点返回 `incomplete_window`。终点后的缺根不改写已确定结果，终点前缺根停止评分。
- 返回 `source/market/interval/event_time/window_start/window_end/bars` 和发言所在 K 线的检查状态；提前结算的 `window_end` 是实际证据终点，不伪装成完整窗口。不把全部 K 线重复送进模型上下文。

施工前先用一个已知历史区间验证 Gate 返回结构、时间戳是开线时间、`from/to` 边界和现货标的一致性。失败时先报告阻塞，不增加多数据源兜底。

## 5. 机械评分规则

纯函数 `score_plan(plan, candles)` 放在新工具文件中，只接收校验通过的计划与完整窗口，不访问存储、不调用 LLM、不复用带持仓生命周期的 `decide_reconcile_action`。

固定口径如下，不让调用方为了得到命中结果调整：

| 项目 | 规则 |
| --- | --- |
| 入场前提 | 发言所在 K 线通过“没有可能漏掉成交”的检查；模拟的是此后仍待成交的计划，不声称用户真的下过单 |
| 限价触发 | 做多 `low <= entry`，做空 `high >= entry`；以原文 entry 为理论成交价，不假设实际滑点 |
| 入场根 | 触及止损按止损；若同根只触及目标，无法确定目标是在入场前还是入场后，返回 `ambiguous` |
| 入场后 | 后续 K 线同时触及止损和目标时按先止损；这是保守 OHLC 口径，不声称还原真实逐笔路径 |
| 跳空入场 | 尚未成交时开盘跳过 entry，不能假设按原价成交；返回 `ambiguous` 并说明可能漏掉成交或亏损，不记成功 |
| 跳空退出 | 已成交后开盘越过止损，记 `stopped`、按开盘价计算毛 R，可小于 -1；越过目标保守按原目标计算。均为 OHLC 模拟口径，不是实盘成交证明 |
| 终点 | 先止损为 `stopped`，先目标为 `target_hit`；24 根未入场为 `untriggered`，入场但未结束为 `unresolved` |
| R 倍数 | 常规止损为 -1；跳空止损做多为 `(open-entry)/abs(entry-stop)`，做空为 `(entry-open)/abs(entry-stop)`；目标为 `abs(target-entry)/abs(entry-stop)`；其他状态为 null，未计费用与资金费 |

不另评分方向、关键位“有效性”或表达质量，不把到窗口结束时的浮盈当成计划盈利；需要实际收益时查询模拟单台账。未来要支持复杂计划，应另行确定业务规则，不偷偷扩展本轮语义。

返回示例：

```json
{
  "status": "success",
  "evidence": {
    "event_id": "ev_xxx",
    "event_time": "2026-10-09T02:27:34Z",
    "plan_quote": "ETHUSDT 4h 做空；入场 2510；止损 2538；止盈 2474。"
  },
  "plan": {"side": "short", "entry": 2510, "stop": 2538, "target": 2474},
  "data_window": {
    "source": "gate.io",
    "market": "spot",
    "interval": "4h",
    "window_start": "2026-10-09T04:00:00Z",
    "window_end": "2026-10-13T04:00:00Z",
    "bars": 24
  },
  "initial_bar_check": "no_entry_touch",
  "rules": {
    "evaluation_scope": "simple_ohlc_plan",
    "same_bar_priority": "stop_first",
    "costs_included": false
  },
  "result": {"plan_result": "stopped", "r_multiple": -1.0}
}
```

以上是展示字段的示例，不是真实 ETH 复盘结果。`rules.evaluation_scope` 为 `simple_ohlc_plan`，合约近似为 `spot_proxy`。这些是工具返回字典，不新建 schema 类型或分层模型。

失败时保留必要的 `status/reason/evidence`，`result` 为 null。状态区分 `not_found`、`unverifiable`、`incomplete_window`、`data_unavailable`、`error`；计算成功不表示建议正确。

`stopped/target_hit/untriggered/unresolved/ambiguous` 属于 `status=success` 下的 `result.plan_result`。合约近似也保留证据与完整窗口，但 `result` 只包含 `entry_touched/stop_touched/target_touched`，三个布尔值表示窗口内价格触及，不表示成交或触及先后；没有 `plan_result/r_multiple`，不能提前以触价当作合约结算。最终回复必须保留范围与歧义，不能换成“方向最终正确”。

不生成工具内的叙事 `summary`，不写用户画像或订单表。工具调用和结果仍由现有会话事件机制记录，无需第二套落库。

## 6. 施工预算与顺序

本轮文档之外，预计业务代码只涉及 4 个文件、新增一个聚焦测试文件：

| 文件 | 修改内容 |
| --- | --- |
| `src/core/prompt.py` | 概率边界、复盘取证和 `touches` 解释，替换会误导的既有示例 |
| `src/tools/trusted_review.py`，新增 | 一个工具函数；局部原文校验和纯评分函数，不新增 domain/review 服务层 |
| `src/tools/market_data.py` | `_fetch_crypto_kline` 内部时间窗参数及有界历史响应检查，复用请求和数据转换 |
| `src/tools/registry.py` | 注册扁平只读工具、授权上下文，复用现有注册方式 |
| `tests/test_trusted_review.py`，新增 | 用少量参数化案例覆盖原文边界、时间窗和评分行为 |

建议生产新增或修改约 200-300 行作为重新评估阈值，不是硬性行数指标；不为压行数牺牲可读性。若需要新增第二个业务模块、大解析器、数据库迁移或多模型流程，先暂停并缩减方案。

按以下顺序交付：

1. 先改提示词并做一次真实模型冒烟：普通分析仍灵活；对这次 ETH “盲测”质疑明确承认不是严格盲测。
2. 工具施工前先做两个小检查：Gate 时间窗接口实测通过；真实历史计划中至少找到一条无需补写就能按上述规则核对的样本。若没有适用样本，先交付提示词，暂停评分工具，不能为了使用工具强制普通对话改成固定模板。
3. 再做工具、历史取数和局部测试；对明确原文走完整核对。实际存在条件或范围的 ETH 建议，应坦白返回不可验证，不能补成简单计划。

关键验收集中在稳定行为，不建设独立 eval 平台：

- 外域事件、非助手事件、blob 缺失和数字角色错配不能评分；同一行被裁掉条件、前文有全局条件或消息中标的/周期不唯一也不能通过。
- 发言所在 K 线可能已触发时不能算未触发；终点前缺根不评分，完整前缀已止损可提前结算，未完成窗口不能记未触发；普通最新行情返回不变。
- 入场前碰目标不能算赢；同根歧义、先止损后走对、跳空亏损和未触发分别保留正确状态；合约近似不输出精确收益。
- 工具执行不调用画像/订单写入；模型不把不可验证、失败或毛 R 包装成方法有效或用户实盘盈亏。

模型冒烟检查工具轨迹和关键业务含义，不断言固定中文句子。无法访问历史行情或模型时，明确交代验证缺口。

施工收尾时对照预算展示关键 diff；按实际实现更新架构日志。部署、推送和重启服务须在用户明确要求后执行。

## 7. 局限与后续触发条件

这不是严格盲测，也不会从根本上消除 LLM 幻觉。原文边界和有限语法会拒绝不少历史自然语言计划；这是公开的不支持，不是系统已经验证这些计划失败。

最终自然语言解释仍可能偏离工具结果。首轮靠短提示和真实冒烟观察；若出现已复现的“把 stopped 说成成功”，再考虑对该缺陷增加局部输出校验，不提前建设全文审计器。

只有用户确实要验证方法前视能力时，再独立设计 cutoff replay：代码切掉未来 K 线、隔离摘要和工具上下文、先冻结计划再获取未来行情；即便如此，也要说明模型预训练历史知识和样本挑选造成的局限，不能把历史 replay 当成真正前瞻实验。

只有累积足够连续样本并确定固定策略规则后，再谈统计、费用与滑点。当前不提供“关键位命中率高”“方法已证明有效”这样的结论。
