# Pi 式上下文管理架构

**状态**：核心运行链路已施工，尚未完成生产发布验收。P0、P2、P3、P5、P6、P7、P9 已落地；P1、P4 的运行路径及 14 个崩溃注入钩子已落地，但完整重复注入矩阵未跑完；P8 已完成删除 gate、tombstone、blob GC 与分区轮转，指标、定期留存和备份恢复工具仍待实施。

截至 2026-09-20，运行时工厂已启用本地 JSONL 事件链路。生产路径不再把旧摘要作为模型上下文，也不向 PostgreSQL 写会话记忆；旧摘要、checkpoint 和 PostgreSQL FactStore 运行时代码已经删除，不保留双写或兼容开关。
**原则**：不以现有实现和迁移成本约束目标设计；旧记忆数据可归档后退出运行链路。
**本版定位**：在既有目标与决策之上，把全部关键协议写成可直接实施的规范。文中所有 MUST/禁止条款都是施工约束，没有“后续再定”的协议；单机部署带来的限制统一写入 §3.6 非目标。

## 1. 决策摘要

MarketAssAgent 的会话记忆改为：

```text
本地 append-only 会话事件日志（唯一真相源）
        ↓
按已激活分支确定性回放
        ↓
最近原文 + 必要时的不可变压缩检查点
        ↓
模型上下文
```

不再把 `turn_summary`、`active_thesis`、`decision_event` 或其他模型生成的结构化字段当作记忆真相。系统持久化真实发生的用户消息、模型请求与响应、工具调用、工具结果和投递结果。搜索索引、分支 head 缓存和上下文投影是可删除重建的派生数据；已经用于模型请求的 compaction checkpoint 是模型可见历史证据，不可修改或删除。

本方案的硬性选择：

- 会话事件采用 Pi 风格的本地 append-only JSONL，不依赖 PostgreSQL 或其他外部服务。
- 入站消息、工具副作用和出站投递都使用稳定幂等键，并采用先记录、后执行协议。
- 历史检索按当前可见域跨会话查询原始事件，不局限于当前 `session_id`，也绝不凭 `actor_id` 跨私聊或群聊。
- 当前分支、分支 head 和模型请求内容都可从追加事件确定；可变缓存不是事实来源。
- PostgreSQL 只服务开单、模拟交易、持仓和行情快照等业务能力，不进入上下文基础链路。
- 旧记忆只导出审计，不导入新日志；切换后只允许向前修复。

该方向参考：

- [Pi session manager](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/session-manager.ts)：append-only 事件、父子关系、分支回放、compaction checkpoint。
- [Pi compaction](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/compaction/compaction.ts)：按 token 阈值压缩并保留近期原文。
- [DeepSeek Harness architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)：Session Event Log 是唯一真相源，模型历史由日志派生。

## 2. 当前方案为什么会产生假回忆

当前链路同时维护完整聊天历史、`recent_message`、每轮 `turn_summary`、`last_snapshot` checkpoint 和 PostgreSQL `analysis_snapshots`。light context 优先读取最近四条摘要，摘要渲染还会截断助手结论，并可能丢掉用户原话。

结果是：

1. 原始消息存在，但默认上下文看不到。
2. 模型生成的摘要逐渐代替原始事实。
3. 历史复盘依赖模型是否主动调用搜索工具。
4. 搜索对象仍是摘要，不是原始对话。
5. 同一内容在多套存储中可能出现顺序、投递状态和文本差异。

ETH 案例中，用户多次明确要求寻找多头机会，但首屏上下文只留下被截断的助手结论。模型随后把“没有看到”说成“没有发生”。这是上下文构造错误，不是模型缺少一个“当前观点”字段。

## 3. 设计边界

### 3.1 唯一真相与不可变范围

会话事实只能由本地事件日志表达。事件提交后不可更新；更正、取消、分支选择、删除请求和恢复结果都追加新事件。

可以删除重建的只有：全文/向量索引、分支 head 投影、幂等索引快照、检索缓存、token 估算缓存和未曾进入模型请求的临时计算。以下内容不可作为缓存删除：

- 原始会话事件。
- 已被 `model/request` 引用的 compaction checkpoint。
- `model/request` 引用的规范化请求 payload。
- 保留期内的工具与投递执行证据。

“逐字复现”指使用当时记录的规范化模型请求 payload 重建 API 输入；不承诺模型供应商在相同输入下产生相同输出。

### 3.2 近期原文优先

模型默认读取按 token 预算选择的最近完整 turn，而不是固定条数的逐轮摘要。不能只保留助手结论而丢失用户问题，也不能拆开工具调用与结果。

### 3.3 历史回忆必须取证

“最近一周”“你之前一直”“我是否说过”等问题必须从用户有权访问的原始事件中检索。检索不到时只能说明证据不足，不能依据摘要补全。

### 3.4 业务状态与会话记忆分离

行情快照、模拟订单和持仓由 PostgreSQL 业务仓库管理。会话日志记录模型当时看到了什么、调用了什么、说了什么，不复制交易状态机。带副作用工具的 `operation_id` 是跨本地日志与业务仓库对账的执行协议，不是交易记忆字段。

PostgreSQL 故障时，依赖它的开单、模拟交易和行情快照工具可以失败或降级，但普通对话、上下文回放、compaction 和历史检索必须继续可用。不得因为业务数据库不可用而拒绝记录用户消息或生成普通回复。

### 3.5 会话可见域

`actor_id` 只回答“谁发了这条消息”，不能决定能检索哪些记忆。上下文读写和跨会话检索必须使用独立的 `visibility_scope + visibility_scope_id`：

| 入口 | `visibility_scope` | `visibility_scope_id` | 可见历史 |
| --- | --- | --- | --- |
| 飞书私聊 | `private` | `open_id` | 仅该用户私聊范围 |
| 飞书群聊 | `group` | `chat_id` | 仅该群已经公开出现的内容 |
| Web | `web` | 已认证用户或显式会话所有者 | 仅该 Web 可见域 |

同一个人从私聊进入群聊视为完全独立的新对话，禁止继承或检索其私聊历史。不同群之间也完全隔离；群内事件保留 `actor_id` 以区分发言者，但任何成员身份都不能扩大群聊检索范围。模型传入的 scope、用户或群 ID 一律不参与授权。

### 3.6 非目标（已接受的限制）

以下限制是本架构主动接受的结果，不视为缺陷，也不在实施阶段补救：

| 非目标 | 明确含义 |
| --- | --- |
| 多主机并发写 | 同一 `session_id` 只允许一台主机上的进程写入。不实现分布式锁、租约或共识。 |
| 网络文件系统 | 不支持 NFS、SMB、overlayfs 等不保证本地 `flock`、原子 `rename`、`fsync` 语义的文件系统。启动自检失败即拒绝启动。 |
| 跨事件事务 | 不提供多事件 ACID。每条事件独立持久化，状态机必须能从任意事件边界恢复。 |
| exactly-once 投递 | 供应商不支持幂等键且不可查询时只提供 at-least-once 或人工确认，不宣称 exactly-once。 |
| 输出可复现 | 只保证模型请求输入逐字可复现，不保证模型输出可复现。 |
| 全局全序 | 只有 session 内 `seq` 全序。跨 session 使用 `(occurred_at, event_id)` 稳定序，不是因果序。 |
| 同 session 并行 turn | 同一 session 的 turn 串行执行。并发入站排队或返回 busy，不并行编排。 |
| 旧记忆导入 | 旧 `turn_summary` / `last_snapshot` 只导出审计，不进入新日志。 |
| 在线水平扩容 | 不做本地日志与 PostgreSQL 双写过渡；扩容时整体替换权威存储（§16.4）。 |
| 字段级加密 | 静态加密由宿主磁盘/文件系统负责，事件层只做租户目录隔离与不可逆身份 hash。 |

## 4. 规范事件信封与 schema 版本

### 4.1 信封字段

每行 JSONL 是一个完整事件，信封字段固定如下。未列出的顶层字段一律拒绝写入（写入器严格模式），读取器保留但不投影。

| 字段 | 类型 | 必填 | 规范 |
| --- | --- | --- | --- |
| `format_version` | int | 是 | 信封版本，当前值 `1`。信封结构变化才升版。 |
| `event_id` | string | 是 | `ev_` + 40 位小写 hex，由 §4.3 确定性派生。 |
| `session_id` | string | 是 | `sess_` + 26 位 Crockford base32。 |
| `seq` | int | 是 | ≥ 1，session 内单调递增且无空洞（§5.4）。 |
| `tenant_id` | string | 是 | 明文租户标识；目录名使用其 hash。 |
| `visibility_scope` | `"private"` \| `"group"` \| `"web"` | 是 | 事件所属可见域类型。 |
| `visibility_scope_id` | string | 是 | 私聊为 `open_id`，群聊为 `chat_id`，Web 为已认证所有者。 |
| `actor_id` | string \| null | 是 | 事件发起者；系统事件为 `null`，不得用于扩大检索范围。 |
| `branch_id` | string | 是 | `br_` + 26 位 base32；主分支由 `session/header` 声明。 |
| `parent_event_id` | string \| null | 是 | 仅 `session/header` 为 `null`。 |
| `event_type` | string | 是 | `<domain>/<name>`，见 §5.1。 |
| `event_class` | `"core"` \| `"aux"` | 是 | 决定未知类型的处理方式（§4.4）。写入器按 §5.1 表填写。 |
| `occurred_at` | string | 是 | RFC 3339 UTC 毫秒，`2026-09-20T03:04:05.123Z`。业务发生时刻。 |
| `recorded_at` | string | 是 | 同格式，落盘时刻，由写入进程时钟产生。 |
| `idempotency_scope` | string | 是 | §4.3 枚举之一。 |
| `idempotency_key` | string | 是 | 64 位小写 hex，§4.3 公式产出。 |
| `schema_version` | int | 是 | 该 `event_type` 的 payload 版本，从 `1` 起。 |
| `payload` | object \| null | 条件 | 内联 payload，规范化编码后 ≤ 64 KiB。 |
| `payload_blob_ref` | object \| null | 条件 | `{algo:"sha256", hash, bytes, media_type, projection}`，见 §6.4。 |
| `producer` | object | 是 | `{component, version, host_id, pid}`，`host_id` 为主机标识 hash。 |
| `record_checksum` | string | 是 | `sha256:` + 64 位小写 hex，见 §4.2。 |

`payload` 与 `payload_blob_ref` 至少有一个非空；两者同时存在时，`payload` 只能承载有界投影与元数据，原文以 blob 为准。

时间语义硬规则：

- session 内排序权威是 `seq` 与父子链，**禁止**用 `occurred_at` 做 session 内排序。
- 跨 session 排序与时间窗过滤使用 `occurred_at`，并在窗口两端放宽 `max_clock_skew = 2s`。
- `recorded_at` 相对同 session 上一条回退时，照实记录并上报 `context_clock_regression_total`，不修改时间戳。

### 4.2 规范化编码与校验和

`canonical_json(x)` 定义为 RFC 8785 JCS 子集：

1. UTF-8 编码，无 BOM，无多余空白。
2. 对象键按 UTF-16 码元序升序，禁止重复键。
3. 字符串使用最短合法转义；非 ASCII 字符直出，不使用 `\uXXXX`。
4. 数字只允许 IEEE-754 可精确表示的整数与有限小数；禁止 `NaN`、`Infinity`、前导 `+`、指数形式。超出 `2^53-1` 的数值必须以字符串承载。
5. 禁止裸换行；记录内的换行一律出现在 JSON 字符串转义中。

校验和：

```text
record_checksum = "sha256:" + hex(sha256(canonical_json(envelope_without_record_checksum)))
```

`envelope_without_record_checksum` 是删除 `record_checksum` 键后的完整信封（含 `payload` / `payload_blob_ref`）。落盘行 = `canonical_json(完整信封)` + 单个 `\n`。行尾换行不参与校验和。

`record_checksum` 只覆盖内联信封。blob 原文完整性由 `payload_blob_ref.hash` 覆盖，读取 blob 时必须重算并比对（§6.4）。

### 4.3 幂等作用域与 event_id 派生

所有事件都带幂等键，`event_id` 一律确定性派生，不使用随机 UUID：

```text
idempotency_key = hex(sha256(canonical_json(key_object)))
event_id        = "ev_" + hex(sha256(canonical_json({
                      "session_id": session_id,
                      "scope": idempotency_scope,
                      "key": idempotency_key
                  })))[0:40]
```

| `idempotency_scope` | `key_object` 字段 |
| --- | --- |
| `session_header` | `session_id` |
| `inbound` | `transport`, `tenant_or_app_id`, `external_message_id` |
| `model_request` | `session_id`, `branch_id`, `parent_event_id`, `request_content_hash` |
| `assistant_message` | `session_id`, `model_request_event_id`, `provider_response_id` 或（缺失时）`response_content_hash` |
| `assistant_local_message` | `session_id`, `turn_user_event_id`, `reason` |
| `assistant_attempt` | `session_id`, `model_request_event_id`, `attempt_ordinal` |
| `tool_call` | `operation_id` |
| `tool_call_started` | `operation_id`, `attempt_no` |
| `tool_result` | `operation_id` |
| `tool_reconciliation` | `operation_id`, `reconcile_nonce` |
| `delivery_plan` | `transport`, `tenant_or_app_id`, `destination`, `assistant_event_id` |
| `delivery_started` | `delivery_planned_event_id`, `attempt_no` |
| `delivery_result` | `delivery_planned_event_id` |
| `delivery_reconciliation` | `delivery_planned_event_id`, `reconcile_nonce` |
| `branch_created` | `session_id`, `fork_parent_event_id`, `new_branch_id` |
| `branch_activated` | `session_id`, `branch_id`, `activation_nonce` |
| `compaction` | `session_id`, `branch_id`, `covered_to_event_id`, `checkpoint_content_hash` |
| `turn_aborted` | `session_id`, `turn_user_event_id`, `abort_nonce` |
| `session_label` | `session_id`, `label_nonce` |
| `session_admin` | `session_id`, `admin_action`, `admin_nonce` |

`*_nonce` 由调用方生成并在整条重试链上复用；同一次逻辑操作的重试必须携带同一 nonce，否则会产生第二条事件。缺少稳定外部 ID 的入口必须自行生成 request ID 并回传给重试方（§7.1）。

由此得到统一的重复写语义：**追加时若 `event_id` 已存在，返回既有事件并标记 `deduplicated=true`，不追加第二行**（§6.2 步骤 3）。

### 4.4 schema 演进与未知类型

- 信封由 `format_version` 管理；payload 由 `event_type + schema_version` 管理。两者独立升版。
- payload 只允许向后兼容变更：新增可选字段、放宽枚举下游语义。删除字段、改字段含义、收紧枚举必须升 `schema_version`。
- 读取器按 `(event_type, schema_version)` 查投影表：
  - 已知：正常投影。
  - 未知 `schema_version` 且 `event_class="aux"`：原样保留，跳过投影，计入 `context_unknown_event_total`。
  - 未知 `schema_version` 且 `event_class="core"`：**fail closed**，该 session 进入 `degraded_unreadable`，拒绝构造上下文并报警。
  - 未知 `event_type`：按信封上的 `event_class` 走上面两条。信封自带 class 使未知类型的判定不依赖类型表。
- `format_version` 高于读取器支持的最大值：无条件 fail closed，不猜测信封结构。
- 升级顺序固定为“读取器先兼容、再写新版本”，两者之间至少间隔一次完整发布（§16.3）。

## 5. 事件、顺序与分支

### 5.1 事件目录

| `event_type` | class | 说明 |
| --- | --- | --- |
| `session/header` | core | session 首条事件，声明 `main_branch_id`、传输来源和创建时间；租户与可见域由事件信封记录。 |
| `user/message` | core | 完整用户输入与入站身份、附件 blob 引用。 |
| `model/request` | core | 一次实际发送的规范化请求（内联或 blob）、模型标识、参数、prompt 版本、所用 checkpoint。 |
| `assistant/message` | core | 一次成功完成并提交的完整模型响应，含供应商 tool call ID。 |
| `assistant/local_message` | core | 未调用模型时由运行时生成并对外投递的确定性提示，例如上下文超限或副作用结果不确定。 |
| `assistant/attempt` | aux | 未形成已提交工具执行计划的失败/取消/截断生成。 |
| `tool/call_planned` | core | 执行前记录 `operation_id`、工具名、`tool_version`、`effect_class`、完整参数与 `args_hash`。 |
| `tool/call_started` | core | 外部调用**发起前**最后一条记录，含 `operation_id`、`attempt_no`、`started_at`。 |
| `tool/result` | core | 与 call 一一配对的终态结果。 |
| `tool/reconciliation` | core | 对既有 `unknown` 结果的后续对账判定，取代其上下文语义。 |
| `delivery/planned` | core | 出站投递计划，持久化后才允许发送。 |
| `delivery/started` | core | 实际发送**发起前**最后一条记录，含 `delivery_planned_event_id`、`attempt_no`、`started_at`。 |
| `delivery/result` | core | 外部投递终态。 |
| `delivery/reconciliation` | core | 对既有 `unknown` 投递的后续判定。 |
| `context/compaction` | core | 不可变 checkpoint。 |
| `branch/created` | core | `new_branch_id` + `fork_parent_event_id`。 |
| `branch/activated` | core | 目标 `branch_id` + `activation_nonce`。 |
| `turn/aborted` | core | 本轮在无模型响应的情况下终止，含原因与最后 attempt 引用；可随后追加本地错误提示。 |
| `session/label` | aux | 人工或自动标签。 |

补充约定：

- 所有修正均追加新事件，不原地修改旧事件。
- `assistant/attempt`、`turn/aborted`、`session/label` **不进入模型上下文**，只进入审计与指标。`assistant/local_message` 作为用户确实收到的会话内容进入后续上下文，但不能伪装成供应商响应。
- `tool/call_started` 与 `delivery/started` 是 `core`（未知版本必须 fail closed，因为它们承载「是否已发起外部调用」这一安全语义），但**不进入模型上下文** —— 它们只驱动恢复判定。`event_class` 决定未知类型的处理方式，与是否进入上下文是两件事，后者由 §9.1 装载集合单独规定。
- `tool/reconciliation` 与 `delivery/reconciliation` 进入上下文，并在投影时覆盖被引用事件的状态。
- 不得用 `assistant/attempt` 隐藏已执行工具：只要任一 `tool/call_planned` 已提交，本次生成必须落为 `assistant/message`。
- `tool/call_planned` 必须把规划时刻的 `effect_class`、`tool_version` 和 `args_hash` 固化进 payload。恢复流程**只读事件中的这些字段**，禁止回查可能已随发布变化的工具注册表（§8.2）。

### 5.2 事件配对与结构约束

追加前在锁内校验下列不变量，违反即拒绝写入并返回 `InvariantViolation`：

1. `session/header` 必须是 `seq=1` 且唯一。
2. `parent_event_id` 必须存在于同一 session，且 `parent.seq < self.seq`。
3. 同一 `branch_id` 内，任一事件最多有一个同分支子节点；出现第二个子节点必须先有解释它的 `branch/created`。
4. `tool/call_planned.assistant_event_id` 必须指向同 session 已存在的 `assistant/message`，且该 provider tool call ID 在其 payload 中存在；`effect_class`、`tool_version`、`args_hash` 三个字段必须齐备且非空。
5. `tool/call_started` 必须引用已存在的 `tool/call_planned`，且该 call 尚无终态结果；`attempt_no` 从 1 起、同一 `operation_id` 内严格递增且无空洞。
6. `tool/result` 必须引用已存在的 `tool/call_planned`，且该 call 尚无终态结果。状态为 `interrupted` 时该 call **不得**存在任何 `tool/call_started`；状态为 `succeeded`、`failed`、`unknown`、`reconciled` 时必须存在至少一条 `tool/call_started`（`pure_query` 的本地重放同样要先写 started）。
7. `tool/reconciliation` 只能引用状态为 `unknown` 的 `tool/result`。
8. `delivery/planned.assistant_event_id` 必须指向已存在的 `assistant/message` 或 `assistant/local_message`。
9. `delivery/started` 必须引用已存在且无终态结果的 `delivery/planned`；`attempt_no` 规则同第 5 条。
10. `delivery/result` 必须引用已存在且无终态结果的 `delivery/planned`；非 `interrupted` 的终态必须存在至少一条 `delivery/started`。
11. `branch/activated.branch_id` 必须已由 `session/header` 或 `branch/created` 声明。
12. `context/compaction.first_kept_event_id` 必须存在，且 `covered_from_event_id ≤ covered_to_event_id < first_kept_event_id`（按 `seq` 比较）。
13. `model/request` 引用的 checkpoint 必须存在且属于当前分支可达集合。

### 5.3 并发追加协议

每次追加先获取该 session 的 OS 文件锁，再读取分支状态。调用者必须提交 `expected_parent_event_id`：

1. 从事件关系推导目标分支当前唯一叶子。
2. 若叶子不等于 `expected_parent_event_id`，返回 `ParentConflict`，由上层重新读取后决定重试或建分支。
3. 若一致，插入新事件并提交；`seq` 决定 session 内稳定顺序。

锁防止同进程和多实例并发写出双 head，`expected_parent_event_id` 防止使用陈旧上下文提交。`ParentConflict` 与 `deduplicated=true` 是不同结果：前者要求调用方重读，后者表示本次操作已完成。

### 5.4 seq 与 head 分配

- `seq` 是**文件属性**而非分支属性：同一 session 的所有分支共用一条递增序列，`session/header` 为 1，此后每条 +1，不允许空洞。
- 分配只能在持锁状态下完成：`seq = last_seq + 1`，其中 `last_seq` 来自“索引快照 + 尾部补扫”（§6.2 步骤 2），不得来自进程内缓存的乐观值。
- 分区轮转（§15.2）跨文件继续同一序列，`seq` 在整个 session 范围内连续。
- head 不是被分配的，而是被推导的：每个分支的 head = 该分支中没有同分支子节点的唯一事件。

### 5.5 分支真相与可重建投影

创建分支必须追加 `branch/created`（含 `new_branch_id`、`fork_parent_event_id`）。切换分支必须追加 `branch/activated`（含目标 `branch_id`、`activation_nonce`）。当前分支定义为该 session 中 `seq` 最大的 `branch/activated` 的目标；不存在时为 `session/header.main_branch_id`。

重建算法（唯一权威实现，投影文件只是它的缓存）：

```text
rebuild(session):
  active = header.main_branch_id
  children = {}                      # parent_event_id -> [event_id]，按 seq 升序
  by_id = {}
  for ev in scan_all_parts(session):         # 按 seq 升序
      verify_envelope(ev)                    # checksum / seq 连续 / 不变量
      by_id[ev.event_id] = ev
      children[ev.parent_event_id].append(ev.event_id)
      if ev.event_type == "branch/activated": active = ev.payload.branch_id
  heads = {}
  for b in declared_branches:
      leaves = [e for e in by_id.values()
                if e.branch_id == b and not any(c.branch_id == b for c in children[e.event_id])]
      assert len(leaves) == 1                # 违反即 fail closed
      heads[b] = leaves[0].event_id
  return {active_branch_id: active, branch_heads: heads, last_seq: max_seq}
```

存在多个分支叶子时只回放已激活分支，不以“最后更新时间”猜测。head 投影文件 `sessions/<tenant_hash>/<scope_hash>/<session_id>.head.json` 结构为：

```json
{"format_version":1,"session_id":"...","last_seq":1234,"last_valid_offset":987654,
 "active_branch_id":"br_...","branch_heads":{"br_...":"ev_..."},
 "source_fingerprint":"sha256:<最后一条事件的 record_checksum>"}
```

读取投影前必须校验 `last_seq`、`last_valid_offset` 与文件实际尾部一致且 `source_fingerprint` 匹配；任一不符则丢弃投影并全量重建。投影只能在持锁时以“写临时文件 → `fsync` → `rename` → `fsync` 父目录”方式更新，损坏或缺失不影响权威数据。

## 6. 本地事件存储契约

### 6.1 文件布局

```text
runtime/data/context/
  sessions/<tenant_hash>/<scope_hash>/<session_id>.jsonl          # part 0
  sessions/<tenant_hash>/<scope_hash>/<session_id>.p<N>.jsonl     # 轮转分区
  sessions/<tenant_hash>/<scope_hash>/<session_id>.parts.json     # 分区清单
  sessions/<tenant_hash>/<scope_hash>/<session_id>.head.json      # head 投影（可重建）
  indexes/<tenant_hash>/<scope_hash>/<session_id>.idx.json        # 幂等索引快照（可重建）
  indexes/<tenant_hash>/<scope_hash>/search/                      # 倒排/向量索引（可重建）
  blobs/<tenant_hash>/<aa>/<bb>/<sha256>                         # aa/bb 为 hash 前四位
  blobs/<tenant_hash>/_tmp/<uuid>                                # blob 暂存
  blobs/<tenant_hash>/_trash/<sha256>.<ts>                       # GC 暂存
  locks/sessions/<session_id>.lock                               # 单 session 排他锁
  locks/scopes/<tenant_hash>/<scope_hash>.gate                    # 可见域 gate（SH/EX）
  locks/scopes/<tenant_hash>/<scope_hash>.gate.intent             # 删除意向标记，防写者饥饿
  locks/_gc.lock
  audit/<tenant_hash>/retention.jsonl                            # 留存/删除 tombstone
  audit/<tenant_hash>/erased/<scope_hash>.json                   # 已删除 session_id 墓碑集合
  quarantine/<tenant_hash>/<scope_hash>/<session_id>.<ts>/       # 中部损坏隔离副本
```

`scope_hash = sha256(tenant_salt || visibility_scope || visibility_scope_id)` 前 32 位 hex；salt 每部署一份并随备份保管。原始租户、可见域和 actor 身份保存在受保护的事件内容中。目录权限 `0700`，文件 `0600`。

启动自检（失败即拒绝启动，不降级）：`flock` 可用、`rename` 原子、`fsync` 对文件与目录均可用、文件系统非网络挂载、剩余空间高于 `min_free_bytes`。

### 6.2 追加协议

blob 必须在取锁之前完成落盘（§6.4）。锁内只做本地计算与写入，**禁止**模型调用、工具执行、网络 I/O 与跨 session 取锁。

1. 按 §6.3 的锁顺序取 scope gate 的**共享锁**，再对 `locks/sessions/<session_id>.lock` 取 `flock(LOCK_EX)`。
2. 加载索引快照（若 `last_seq`/`last_valid_offset`/`source_fingerprint` 校验通过），再从 `last_valid_offset` 扫描到 EOF，刷新 `event_id`、`(scope,key)`、父子关系与 `last_seq`。
3. 若 `event_id` 已存在：释放锁，返回既有事件并置 `deduplicated=true`。
4. 校验 `expected_parent_event_id`（§5.3）与全部结构不变量（§5.2）。
5. 分配 `seq = last_seq + 1`，填 `recorded_at`，计算 `record_checksum`，编码为单行。
6. 检查轮转条件（§15.2），必要时先完成轮转。
7. 记录当前 `offset_before = lseek(fd, 0, SEEK_END)`，以 `O_APPEND` 单次 `write()` 写入整行。
8. 若发生短写或 `write` 报错：在同一锁内 `ftruncate(fd, offset_before)`、`fsync`，返回 `StorageError`，本轮视为未被接受。
9. `fsync(fd)`。只有 `fsync` 成功才向调用者确认提交。
10. 更新内存索引、`last_valid_offset`，异步落 head 投影与索引快照（失败只告警，不影响提交结果）。
11. 按取锁的逆序释放 session 锁与 scope gate。

组提交：仅允许在同一次持锁内追加同一 session 的多条事件后执行一次 `fsync`，且所有这些事件在该 `fsync` 成功后统一确认；不得跨锁批处理。

多个进程必须使用同一 OS 文件锁协议，不允许各自无锁追加。索引只是投影，每次持锁后都要补扫未知尾部，不能依赖进程内缓存保证唯一性。

### 6.3 锁协议、读路径与崩溃恢复

**两级锁与全局锁顺序**。锁只有两级，任何路径都必须按下列顺序自左向右获取，且**禁止**反向获取，因此不存在环路、不存在死锁：

```text
locks/_gc.lock  →  locks/scopes/<tenant_hash>/<scope_hash>.gate  →  locks/sessions/<session_id>.lock
```

| 路径 | gate 模式 | session 锁 | 同时持有的 session 锁数 |
| --- | --- | --- | --- |
| 常规 append（§6.2） | `LOCK_SH` | `LOCK_EX`，单把 | 1 |
| 读取 / 检索 | `LOCK_SH` | 不取 | 0 |
| 分区轮转 | `LOCK_SH` | `LOCK_EX`，单把 | 1 |
| scope 删除（§14） | `LOCK_EX` | **完全不取** | 0 |
| blob GC | 只取 `_gc.lock` | 不取 | 0 |

关键约定：**任一进程在任一时刻最多持有一把 session 锁**，这条规则对所有路径无例外。删除流程不再逐个获取 session 锁 —— 它改为取可见域 gate 的排他锁，这足以排斥该 scope 下所有 session 的 append（每个 append 都必须先持有同一 gate 的共享锁），因此无需枚举 session，也不会随 session 数量增长而阻塞或死锁。

**gate 与 rename 的竞态排除**。删除的 `rename` 只能在持有 gate `LOCK_EX` 期间执行。由于 append 在**打开任何 session 文件之前**就已持有 gate `LOCK_SH`，两者互斥，于是：

- `rename` 进行时，不存在任何处于「已校验路径、尚未写入」窗口的 append。
- `rename` 完成后新发起的 append 会取 gate 时阻塞，等 gate 释放后发现 scope 目录已不存在，返回 `SessionErased`，**不重建目录**。墓碑文件 `audit/<tenant_hash>/erased/<scope_hash>.json` 记录已删除的 `session_id` hash 集合与删除时间：写入器禁止为墓碑中的 `session_id` 隐式 `mkdir`；只有 `session/header` 的创建路径可建目录，且必须在持有 gate `LOCK_SH` 时确认目标 `session_id` 不在墓碑中。因此删除不会阻止新建其他 session，只阻止已删除 session 被复活。
- 已持有文件描述符的 append 即使在 `rename` 后完成写入，也只会写进已被移走的 inode，随隔离目录一并删除，不会复活用户数据。

**写者饥饿与意向标记**。`flock` 不保证写者优先，持续的 append 或读取可能让 gate `LOCK_EX` 长期取不到。删除流程先创建 `<scope_hash>.gate.intent`（内含 `requested_at`、`policy_id`），append 和新读取在取 gate 共享锁**之前**检查该标记：存在时直接返回 `StoreBusy`，从而在有界时间内排空在途操作。intent 标记在删除完成或超时（默认 10 min）后删除；超时会释放 gate、删除标记并告警 `context_erase_gate_timeout_total`，删除任务稍后重试，不留下半删除状态。

**锁等待与超时**：gate 与 session 锁默认超时均为 5 s，指数退避加抖动重试 3 次（总计 ≤ 15 s），仍失败返回 `StoreBusy`，入站层对用户返回“系统繁忙请重试”，不丢弃消息。目标持锁时长 p99：session 锁 ≤ 20 ms，gate 共享锁 ≤ 25 ms，gate 排他锁 ≤ 60 s（删除是罕见操作，期间该用户不可写入是预期行为）。

**锁文件生命周期**：锁文件与 gate 文件均为零长度，创建后不得截断或删除；进程退出即自动释放。回收只允许由 GC 在持有 `locks/_gc.lock` 时，对 `LOCK_EX|LOCK_NB` 立即成功且 mtime 超过 7 天的锁文件执行 `unlink`。

**读路径**：读取与检索在整个读取期间持有对应 scope gate 的 `LOCK_SH`，但不取 session 锁。读取时先记录当前文件大小 `S`，只解析 `[0, S)` 内的完整行；遇到尾部半行直接忽略，**禁止**读取器截断或修复文件。这样不会阻塞同为共享 gate 的常规追加，却能保证删除取得 `LOCK_EX` 后不再有旧文件描述符向调用方返回已删除内容。

**启动与首次打开恢复**：持锁后自尾向前校验 JSON、信封、`seq` 连续性与 `record_checksum`：

| 损坏形态 | 判定 | 动作 |
| --- | --- | --- |
| 文件尾部无 `\n` 结尾的残行 | 尾部损坏 | 截断至最后一个有效行尾，`fsync` 文件与父目录，追加独立 `tail_truncated` 运维审计记录 |
| 最后一行 checksum 失败或 JSON 非法 | 尾部损坏 | 同上 |
| 非尾部行 checksum 失败、JSON 非法、`seq` 跳跃或重复 | 中部损坏 | **fail closed**：整个 session 标为 `quarantined`，复制到 `quarantine/`，向独立运维审计日志写一条 `session_quarantined` 记录（不是 session 事件），`append` 与上下文构造对该 session 抛 `Quarantined`，等待从备份恢复 |
| 引用的 blob 缺失但未过期 | 数据不完整 | 该事件按 `raw_content_unavailable` 投影并告警；不隐式删除事件 |
| head 投影/索引快照校验失败 | 派生损坏 | 丢弃并全量重建，不影响权威数据 |

中部损坏禁止“跳过后继续回放”。新建、截断、轮转和原子替换后都必须 `fsync` 文件及父目录。

多个相关事件不假装具有数据库事务：每条事件独立持久化，Agent 状态机必须能从任意事件边界恢复。任何外部副作用只能发生在对应 `tool/call_planned` 已完成 `fsync` 之后。

### 6.4 blob 原子提交与 GC

**写入（必须先于引用事件的追加完成）**：引用 blob 的调用方先取得 `_gc.lock` 共享锁，并保持到引用事件完成 `fsync`。锁顺序仍为 `_gc.lock → scope gate → session lock`。

1. 计算内容 `sha256`，得到目标路径。
2. 目标已存在且 hash、长度一致：在共享 GC 锁保护下直接复用，不重写。
3. 否则写 `blobs/<tenant_hash>/_tmp/<uuid>`，`fsync` 文件。
4. `rename` 到最终路径（同文件系统内原子），`fsync` 最终目录与其父目录。
5. 返回 `{algo, hash, bytes, media_type, projection}` 供事件引用。

事件不得引用不存在或 hash 不匹配的 blob。读取 blob 时必须重算 hash 比对，不一致按数据不完整处理并告警。

**GC（mark-and-sweep，不使用引用计数文件）**：

- 触发：每日一次或 blob 目录超过 `blob_gc_threshold_bytes`。持 `locks/_gc.lock` 排他锁；引用 blob 的追加持共享锁，因此 mark/sweep 不会与“复用旧 blob 后尚未提交引用事件”的窗口并发。
- mark：扫描该租户全部 session 全部分区，收集所有 `payload_blob_ref.hash`（含隔离区与未激活分支）。
- sweep：候选 = 未被引用 ∧ `mtime` 早于 `now - blob_gc_grace`（默认 24 h）。`blob_gc_grace` 必须大于“blob 落盘到事件提交”的最大允许间隔（默认 5 min），因此 mark 期间新写入的 blob 永远不会被误删。
- 删除先 `rename` 到 `_trash/`，保留 24 h 后物理删除，期间可人工回收。
- `_tmp/` 中超过 1 h 的残留文件直接删除。
- GC 不删除任何被引用 blob；留存到期删除走 §14，不走 GC。

## 7. 幂等状态机

五条链路各自有显式状态机，状态只能由事件推导，不存在独立的可变状态表。

### 7.1 入站

幂等键为 `(transport, tenant_or_app_id, external_message_id)`（scope=`inbound`）。

```text
absent --append user/message--> accepted --启动 turn--> running --终态--> settled
  ^ 重投命中 event_id 已存在 -> 返回已有处理状态或最终回复，不追加、不重启 loop
```

- 适配层在 session 文件锁内完成查重与追加，二者不可分离。
- 缺少稳定外部消息 ID 的入口（Web、CLI）必须生成 request ID 并回传给调用方，由调用方在重试时携带；**禁止**用消息文本或时间近似去重。
- 同一 session 已有 turn 在 `running` 时，新入站排队，队列上限 8；超限返回 busy 并保留用户消息事件，由后续 turn 消费。

### 7.2 模型请求与 attempt

```text
model/request 提交
   ├─ 流式成功且已提交 assistant/message      -> committed
   ├─ 生成失败/取消/截断且无 tool/call_planned -> assistant/attempt(attempt_ordinal+1) -> 可重试
   └─ 已提交任一 tool/call_planned            -> 必须落 assistant/message，禁止改判 attempt
```

- 重试若请求内容逐字不变，`model_request` 幂等键命中同一事件，不产生第二条 `model/request`；`attempt_ordinal` 递增。
- 请求内容变化（追加了工具结果等）即产生新的 `model/request`。
- 每个用户 turn 的 attempt 上限为 3；达到上限追加 `turn/aborted`（含 `reason` ∈ `provider_error`、`timeout`、`cancelled`、`context_overflow`、`policy_refused`、`agent_loop_limit`、`indeterminate_tool_result`），对用户返回明确错误。
- `assistant/attempt` 与 `turn/aborted` 不进入模型上下文，避免把失败草稿当历史事实。

### 7.3 工具与副作用

`operation_id` 按稳定输入生成，不随进程重启变化：

```text
operation_id = hash(session_id, turn_user_event_id, assistant_event_id,
                    provider_tool_call_id, tool_name, tool_version)
```

```text
planned ──(无 started，可安全按策略处置)──> interrupted | 首次执行
planned ──append tool/call_started + fsync──> started ──调用外部──> succeeded | failed | unknown
started  ──崩溃后恢复：结果不确定，禁止盲目重放──> 按 effect_class 对账 ──> reconciled | unknown
unknown  ──后续对账──> tool/reconciliation(succeeded | failed)
```

`tool/call_started` 必须在**发起外部调用之前**完成 `fsync`，这是区分「尚未调用」与「可能已调用」的唯一依据：

- **planned 无 started**：外部调用一定尚未发起，恢复时可安全按策略执行或中止（`interrupted`），对 `opaque_effect` 也是安全的。
- **started 无 result**：外部调用可能已经到达对端，**结果不确定**，一律禁止盲目重放，必须按 `effect_class` 对账（下表）。
- 每次重试（含对账后的补发）都要先追加 `attempt_no` 递增的新 `tool/call_started`，使「共发起过几次外部调用」可从日志精确计数。

工具按副作用能力分四类。`effect_class` 在工具注册表声明（缺失即视为 `opaque_effect`，最保守），并在 `tool/call_planned` 提交时**固化进事件**；恢复只读事件中的值，不回查注册表，因此工具改版或降级发布不会把旧的 `opaque_effect` 调用误判成可重放：

| `effect_class` | 含义 | planned 无 started | started 无 result |
| --- | --- | --- | --- |
| `pure_query` | 无副作用 | 直接执行 | 同 `operation_id` 重放 |
| `idempotent_write` | 接受 `operation_id` 或适配层建唯一执行记录 | 直接执行 | 查执行台账；未执行则同 ID 重试 → `reconciled` / `succeeded` / `failed` |
| `queryable_effect` | 有副作用但可按 ID 查询 | 直接执行 | 按 ID 向外部查询 → `reconciled` / `unknown` |
| `opaque_effect` | 既不幂等也不可查询 | 直接执行或 `interrupted`，均安全 | **禁止**重放与自动重试，记 `unknown`，转人工确认 |

所有重试复用同一 `operation_id`。`unknown` 不等于失败，模型不得据此声称订单未创建或消息未发送。

### 7.4 出站投递

投递键为 `hash(transport, tenant_or_app_id, destination, assistant_event_id)`。

```text
planned ──(无 started)──> 可安全发送或 interrupted
planned ──append delivery/started + fsync──> started ──实际发送──> delivered | failed | unknown
started ──崩溃后恢复：可能已送达，禁止盲目重发──> 按投递能力对账
unknown ──可对账──> delivery/reconciliation(delivered | failed)
unknown ──不可对账──> 停留 unknown，人工确认，默认不自动重发
```

`delivery/started` 必须在实际调用供应商发送接口之前完成 `fsync`，语义与 §7.3 一致：

- **planned 无 started**：尚未发送，worker 可安全发送，不存在重复回复风险。
- **started 无 result**：可能已送达，按投递能力处置 —— 供应商支持按幂等键查询时先对账再决定，支持幂等键去重时可携带同一投递键重发，两者都不支持时停留 `unknown` 并转人工确认，**默认不自动重发**，避免给用户发两遍。
- 每次重发前追加 `attempt_no` 递增的新 `delivery/started`。

worker 从日志扫描尚无终态结果的计划事件，不维护第二套权威 outbox。供应商既不能查询又不支持幂等键时，只提供 at-least-once 或人工确认语义（§3.5）。

### 7.5 幂等索引

- 索引结构：`(scope,key) -> event_id` 与 `event_id -> (seq, offset)`，进程内 dict，首次打开时全量扫描建立，此后每次持锁按 `last_valid_offset` 增量补扫。追加正确性只依赖“快照 + 补扫”，不依赖快照存在。
- 快照文件 `indexes/.../<session_id>.idx.json` 用于加速冷启动，带 `last_seq` / `last_valid_offset` / `source_fingerprint` 校验门；不匹配即全量重建。
- 内存上限：单 session 索引约 100 B/事件（200k 事件约 20 MiB）。进程同时受两个上限约束，先到者触发逐出：打开 session 数 ≤ 64，索引常驻总字节 ≤ `index_memory_budget_bytes`（默认 512 MiB）。按 LRU 逐出，逐出后再次访问从快照恢复。

## 8. 一次 Turn 的提交协议

### 8.1 提交顺序

```text
提交 user/message（入站去重后）
  -> 构造上下文并提交 model/request
  -> 调用模型
  -> 提交 assistant/message（含 tool calls）
  -> 为每个 call 提交 tool/call_planned 并 fsync
  -> 提交 tool/call_started 并 fsync        ← 外部调用前最后一条记录
  -> 执行工具
  -> 提交 tool/result
  -> 构造下一次 model/request …（循环）
  -> 最终 assistant/message 后提交 delivery/planned 并 fsync
  -> 提交 delivery/started 并 fsync         ← 实际发送前最后一条记录
  -> 发送并提交 delivery/result
```

三条顺序约束都是硬性的，任何一条被绕过都会让恢复无法判定外部状态：

1. 模型输出必须先持久化，才能执行其中的工具调用。
2. `tool/call_planned` 与 `tool/call_started` 必须都已 `fsync`，才能发起外部调用；`delivery/planned` 与 `delivery/started` 必须都已 `fsync`，才能实际发送。
3. `planned` 与 `started` 是两条独立事件、两次 `fsync`，**不得合并**为一条 —— 合并会重新丢失「已规划但尚未调用」这个可安全重试的窗口。

### 8.2 孤儿恢复

启动恢复任务和每轮执行前执行三遍扫描。判定只依据日志中的事件，**所有 `effect_class`、`tool_version`、`args_hash` 均从 `tool/call_planned` 事件读取，禁止回查工具注册表** —— 注册表可能在崩溃与恢复之间随发布变化，依赖它会让旧调用被按新类别误处置。

若注册表当前声明的 `effect_class` 与事件中固化的值不一致：以事件中的值为准，且只允许向**更保守**方向升级（保守序 `pure_query` < `idempotent_write` < `queryable_effect` < `opaque_effect`），禁止降级，并上报 `context_effect_class_drift_total`。

**第一遍**：`assistant/message` 中存在但没有对应 `tool/call_planned` 的 tool call。这类 call 连计划都未落盘，一定尚未执行，可安全补写 planned 事件。

**第二遍**：有 `tool/call_planned`、**无任何 `tool/call_started`**、且无终态结果的 call。外部调用一定尚未发起：

| 处置 | 追加结果 |
| --- | --- |
| 本轮继续执行 | 先写 `tool/call_started`，再正常执行并落终态 |
| 本轮不再继续（turn 已终止或超期） | `interrupted`（不调用工具，对 `opaque_effect` 同样安全） |

**第三遍**：有 `tool/call_started`、无终态结果的 call。外部调用可能已到达对端，**结果不确定**，按事件中固化的 `effect_class` 对账：

| 固化 `effect_class` | 恢复动作 | 追加结果 |
| --- | --- | --- |
| `pure_query` | 追加新 `attempt_no` 的 started 后用同一 `operation_id` 重放 | `succeeded` / `failed` |
| `idempotent_write` | 查执行台账；未执行则追加新 started 并同 ID 重试 | `reconciled` / `succeeded` / `failed` |
| `queryable_effect` | 向外部系统按 `operation_id` 查询，不重放 | `reconciled` / `unknown` |
| `opaque_effect` | 不查询也不重放，交人工确认 | `unknown` |

恢复必须为每个 call 追加一个配对的 `tool/result`，即使结果是 `interrupted` 或 `unknown`，保证发给模型的上下文不含孤立 tool call。上下文构造器在装载前再次断言配对完整性，不完整即拒绝构造（§9.3）。

投递侧执行同构的三遍扫描：无 `delivery/started` 的计划可安全发送；有 `delivery/started` 无结果的计划按 §7.4 的投递能力对账，默认不自动重发。

### 8.3 turn 终止

turn 的终态只有三种，且都可从事件判定：

- `assistant/message` 之后出现终态 `delivery/result` 或 `delivery/reconciliation` → 完成。
- `turn/aborted` → 失败并已告知用户。
- 以上都没有 → 未完成，恢复任务接管：先补齐工具配对，再按 §7.2 决定重试或 abort。

## 9. 上下文构造与精确复现

### 9.1 装配规则

新增唯一的 `SessionContextBuilder`，从已激活分支事件构造模型消息，取代 `build_light_agent_input()` 的摘要首屏。

未压缩时：

```text
当前系统提示词
+ 当前分支最近完整事件
+ 当前用户消息
```

压缩后：

```text
当前系统提示词
+ 最新可用 context/compaction
+ first_kept_event 之后的完整原始事件
+ 当前用户消息
```

装载集合只包含 `user/message`、`assistant/message`、`assistant/local_message`、`tool/call_planned`、`tool/result`（经 `tool/reconciliation` 覆盖后的状态）和被选中的 `context/compaction`；其余事件类型不进入模型输入。

特别地，`tool/call_started` 与 `delivery/started` 虽为 `core`，但**不进入模型上下文** —— 它们记录的是执行过程，不是模型看到过的内容；把发起次数送进上下文既无助于回答用户，又会让重试细节污染历史。它们的 `core` 分级只作用于未知版本时的 fail-closed 行为（§5.1）。

### 9.2 model/request 记录

每次真实调用前追加 `model/request`，保存实际发送给供应商的 UTF-8 请求体字节、内容 hash、HTTP 语义所需参数、模型标识、prompt 版本和所用 `checkpoint_event_id`。请求体规范化后超过 64 KiB 时先落 blob 再引用。历史请求始终引用当时实际使用的 checkpoint，因此可逐字恢复 API 输入；后续 checkpoint 只能影响未来请求。

### 9.3 装载前断言

构造上下文时执行确定性断言，任一失败即拒绝构造并报警，不发送残缺上下文：

1. 每个装载的 `tool/call_planned` 都有配对终态结果。
2. 每个装载的 `tool/result` 的 call 也在装载集合内。
3. checkpoint 的 `first_kept_event_id` 在当前分支可达且 `seq` 有序。
4. 装载集合中不存在 `event_class="core"` 的未知类型或未知 `schema_version`。
5. 装载集合按 `seq` 升序且父子链连通到当前 head。

同时产出本轮 `turn_evidence_index`：`{event_id -> tier}`，供 §12 引用校验使用。tier 的赋值规则确定且互斥，同一事件命中多条时取更强者（`verbatim` > `retrieved` > `checkpoint_cited`）：

| tier | 赋值来源 |
| --- | --- |
| `verbatim` | 事件原文（或其有界投影）本身进入了模型输入 |
| `retrieved` | 由 §11 检索返回并附带 `retrieval_receipt`，原文进入了模型输入 |
| `checkpoint_cited` | 事件本身未装载，只出现在被选中 checkpoint 的 `source_event_ids` 中 |

## 10. Compaction 与超限处理

触发条件：

```text
context_tokens > model_context_window - reserve_tokens
```

初始参数：`reserve_tokens` 取上下文窗口的 20%–25%，近期原文保留 25%–35%。切点只能位于完整 turn 边界，禁止拆开 tool call/result。

### 10.1 checkpoint 内容与持久语义

checkpoint 使用自由文本，并附 `covered_from_event_id`、`covered_to_event_id`、`first_kept_event_id`、输入 token 数、生成模型、`source_event_ids` 与下层 checkpoint 引用。它必须区分用户原话、助手判断和工具事实，不得把条件计划改写为已执行。

持久语义：

- 候选在内存或临时工作区生成与校验，失败候选**不进入事件日志**。
- `context/compaction` 一旦提交即不可变。可以追加新 checkpoint 取代它服务未来请求，但留存期内不得更新或删除旧 checkpoint。
- “最新可用 checkpoint” = 当前分支上 `seq` 最大且 `first_kept_event_id` 仍在当前分支可达的 `context/compaction`。分支切换后不可达的 checkpoint 自动失效，但不删除。
- `model/request` 显式记录实际选用的 `checkpoint_event_id`，历史请求不随新 checkpoint 改变。

### 10.2 token 兜底与超大事件

超限按固定顺序处理，每一步后重算 token，命中预算即停止：

1. 大工具结果原文保留在 blob，仅向模型提供有界投影（默认 ≤ 4 KiB，头尾各半并标注省略字节数）和 hash 引用。
2. 在 turn 边界减少近期原文，但不拆工具对。
3. 对更早区间做分层 compaction，新 checkpoint 引用下层 checkpoint 与原始事件范围。
4. 仍超限时使用带事件引用的抽取式 fallback（按关键词与时间窗抽取原文句段，全部附 `event_id`），不提交被 token 截断或缺少覆盖边界的 LLM 摘要。
5. 单个当前 turn 仍超过模型硬窗口时，停止调用，追加 `turn/aborted(reason="context_overflow")` 并返回明确错误；不得静默丢参数或工具结果。

超大事件的硬阈值：内联 payload > 64 KiB 必须转 blob；单条记录行 > 512 KiB 拒绝写入并要求调用方改用 blob + 投影；单个用户消息超过窗口预算时，原文完整入库，上下文内使用有界投影并明确标注截断。

token 计量：优先使用供应商 tokenizer；不可用时使用本地估算器并按 `estimator_margin`（默认 8%）上浮，估算与实际偏差超过 15% 时上报 `context_token_estimate_drift`。

摘要生成失败、输出截断、引用越界或校验失败时不提交 checkpoint，继续使用上一个有效边界或进入抽取式 fallback。

## 11. 跨会话历史检索

提供统一的 `search_session_history`，直接查询原始事件。授权范围由 `(tenant_id, visibility_scope, visibility_scope_id)` 决定，`session_id` 只是可选过滤条件。

**授权硬规则**：`tenant_id`、`visibility_scope` 与 `visibility_scope_id` 只能来自入站身份上下文，**禁止**从模型工具参数取值；模型传入的任何身份字段一律忽略并记 `context_auth_override_attempt_total`。`actor_id` 不能扩大检索范围。

检索步骤：

1. 在当前可见域目录下的全部 session 日志中按时间、角色、标的和关键词召回；时间过滤使用 `occurred_at` 并在窗口两端放宽 `max_clock_skew`。
2. 扩展为命中事件前后的完整 turn，包括相邻工具调用和结果。
3. 可选本地倒排或语义索引仅负责二次排序；索引丢失时可从原始事件重建，不能成为数据库依赖。索引不可用时自动退化为全量扫描并上报 `context_search_degraded_total`。
4. 返回原始文本、时间、`session_id`、`event_id`、`tier=retrieved` 和证据窗口，并附 `retrieval_receipt`：`{query, time_range, filters, scanned_sessions, total_hits, hit_event_ids, truncated}`。
5. 命中集合超过 `max_hits`（默认 200）时置 `truncated=true`，禁止据此做“全部/从未/共 N 次”结论（§12）。

返回结果全部登记进本轮 `turn_evidence_index`，`tier=retrieved`。

“最近一周是否多次让我找 ETH 多头机会”必须跨会话检索一周内的用户原话，不能只扫当前 session，也不能以 checkpoint 作为最终证据。

## 12. 历史主张校验与事件引用

模型草稿中的历史结论使用内部引用 `[mem:<event_id>]`。运行时执行确定性检查，不做语义判断：

1. **检测**：命中带次数、频率、先后或过往断言的句子，以及“你一直”“我从未”“最近几次”“上次”等触发短语。
2. **引用存在性**：每个 `[mem:<id>]` 必须能解析为真实 `event_id`。
3. **授权**：该事件必须属于当前 `(tenant_id, visibility_scope, visibility_scope_id)`；相同 `actor_id` 不能跨私聊与群聊授权。
4. **装载性**：`event_id` 必须在本轮 `turn_evidence_index` 中。
5. **证据层级**：
   - 普通历史陈述：`tier ∈ {verbatim, retrieved}` 通过；仅 `checkpoint_cited` 触发补查。
   - 次数、频率、“始终/从未”类主张：必须附 `retrieval_receipt`，且 `truncated=false`，声称次数 ≤ `total_hits`，全部被引事件在 receipt 的 `hit_event_ids` 内。
6. **时间一致性**：带时间窗的主张，被引事件 `occurred_at` 必须落在声明窗口内（含 `max_clock_skew` 容差），且 receipt 的 `time_range` 覆盖该窗口。
7. **修复**：任一检查失败，自动执行一次历史搜索并最多进行一次 repair generation。
8. **降级**：修复后仍无有效证据，将该句降级为“当前可见记录不足以确认”，不继续重试。
9. **渲染**：renderer 在对外发送前移除内部引用；审计日志保留主张、引用和校验结果。

误报不会阻止整条回复：非历史性句子直接通过，无法确认的历史句子局部降级。指标记录触发数、补查数、修复成功数和证据不足数，用离线样本持续校准检测器，但不能关闭引用校验。

自动补查属于 `HistoricalClaimGuard` 的内部只读策略，不伪装成模型发起的 tool call；补查结果会完整进入下一条已持久化的 `model/request`，因此仍可逐字审计。模型主动调用 `search_session_history` 时，继续使用标准 `planned → started → result` 工具事件链。两条路径都必须排除当前正在回答的 `user/message`，避免把“我之前是否问过”这句话本身计入历史次数。

## 13. 模块职责与接口

```text
ConversationService
  └── 入站去重、一次 turn 编排、追加投递计划

SessionStore (local append-only JSONL)
  └── append / read_branch / fork / activate / scan / export / rebuild_projection

SessionContextBuilder
  └── 从事件分支派生上下文、产出 turn_evidence_index、提交 model/request

SessionCompactor
  └── 阈值判断、候选校验、追加 checkpoint、分层与抽取式 fallback

SessionHistorySearch
  └── 在当前 visibility scope 内跨会话检索完整 turn，产出 retrieval_receipt

ToolExecutionCoordinator
  └── operation_id、write-before-execute、effect_class 分派、对账与孤儿恢复

DeliveryWorker
  └── 扫描投递计划、幂等投递、超时对账、追加结果

HistoricalClaimGuard
  └── 引用校验、单次补查与降级

RetentionWorker
  └── 留存清理、blob GC、tombstone 审计、备份校验
```

`SessionStore` 的最小接口契约：

```text
append(event_draft, expected_parent_event_id) -> {event, deduplicated}
              raises ParentConflict | InvariantViolation | StoreBusy | StorageError | Quarantined
read_branch(session_id, branch_id=None, since_seq=None) -> iterator[event]   # 无锁快照读
projection(session_id) -> {active_branch_id, branch_heads, last_seq}
put_blob(bytes|stream, media_type) -> blob_ref                               # 必须在 append 前完成
get_blob(blob_ref) -> bytes | RawUnavailable
scan_scope(tenant_id, visibility_scope, visibility_scope_id, time_range, filters) -> iterator[event]
export(session_id) -> jsonl_stream
```

已退出主链路并删除的机制包括：每轮 `turn_summary`、`recent_message` 双写、`last_snapshot` 会话 checkpoint、`search_conversation_summaries` 与 `build_light_agent_input()` 摘要拼装。它们只允许出现在归档设计记录中，不得重新进入 `src/` 运行时代码。

## 14. 留存、删除与 tombstone

默认策略：

- 活跃会话事件在线保留；归档会话事件保留 365 天。
- 大型原始工具 blob 默认保留 90 天；到期后删除 blob 文件，事件中的 hash、长度、有界投影和 `raw_content_unavailable` 状态保留至对应事件到期。
- 模型请求 blob 与其引用事件采用相同保留期，保证保留期内精确复现。
- 交易订单、持仓和监管数据遵循独立业务留存规则，不随会话删除自动清除。

**blob 到期**：删除 blob 文件后向独立运维审计日志追加 `blob_expired` 记录。该记录不是 session 事件，不占用 session `seq`。上下文与检索的权威判定是“blob 文件是否存在且 hash 匹配”，缺失即按 `raw_content_unavailable` 投影，不依赖审计记录是否存在。

**可见域删除请求**（每一步都可重入，中途崩溃后重跑得到相同结果）：

1. 创建 `locks/scopes/<tenant_hash>/<scope_hash>.gate.intent`，使在途 append 和读取在有界时间内收敛到 `StoreBusy`（§6.3）。
2. 取该 scope gate 的 `LOCK_EX`。**不获取任何 session 锁** —— gate 已排斥该 scope 下所有 session 的 append 与读取。
3. 将 scope 的 session 目录原子 `rename` 到隔离区，`fsync` 父目录；随后删除对应索引。持有共享 gate 的旧读取已经排空，因此此刻起不可检索。
4. 物理删除 session 分区、head 投影、幂等索引、检索索引。
5. 原子写入墓碑 `audit/<tenant_hash>/erased/<scope_hash>.json`（已删除 `session_id` hash 集合），使后续 append 不会复活这些 session，但不影响该 scope 新建其他 session（§6.3）。
6. 释放 gate 并删除 intent 标记。
7. 触发一次租户 blob GC；只被该用户引用的 blob 在 grace 后删除，仍被他人引用的共享 blob 保留。
8. 向 `audit/<tenant_hash>/retention.jsonl` 追加 tombstone：`{action:"scope_erased", tenant_hash, scope_hash, session_ids_hash, event_count, byte_count, requested_at, completed_at, policy_id}`，**不含任何原文**。

步骤 3 之后崩溃只会留下待清理的隔离目录，该 scope 数据已不可检索；重跑从步骤 4 继续。步骤 7–8 在 gate 之外执行，因此删除不会长时间阻塞新会话创建。

append-only 只在留存期内、且未执行合法删除的范围内成立；删除后事件、索引和无共享引用的 blob 均不可检索。租户加密边界不允许跨租户去重明文，blob 去重只在同租户目录内发生。

后台任务按文件元数据和事件保留策略清理，并记录不包含原文的删除审计。备份必须覆盖 session 分区、分区清单、blob 与身份 salt，每周执行一次 checksum 校验，每季度执行一次恢复演练（§16.6）。

## 15. 容量、延迟与可观测性

### 15.1 容量假设

| 维度 | 规划值 |
| --- | --- |
| 单事件内联大小 | 典型 1–2 KiB，内联上限 64 KiB，单行硬上限 512 KiB |
| 单 session 事件数 | 软上限 200k，超过触发轮转 |
| 单分区文件 | 软上限 256 MiB |
| 单 session 总量 | 规划 ≤ 2 GiB（约 10 个分区） |
| 单租户活跃 session | 规划 ≤ 20k |
| 进程内打开 session 索引 | LRU，session 数 ≤ 64 且常驻字节 ≤ `index_memory_budget_bytes`（默认 512 MiB），先到者逐出 |
| blob 目录 | 单租户规划 ≤ 200 GiB，超过 `min_free_bytes`（默认 10 GiB）时拒绝写入新 blob 并告警 |

### 15.2 分区轮转

- 触发：当前分区字节数 ≥ 256 MiB 或事件数 ≥ 200k。
- 步骤（持锁内）：`fsync` 当前分区 → 原子替换 `<session_id>.parts.json`（含每个分区的 `first_seq`、`last_seq`、`byte_size`、`last_checksum`）→ 创建下一分区文件 → `fsync` 父目录。
- 只有最后一个分区可追加；`seq` 跨分区连续；读取按 `parts.json` 顺序拼接。
- `parts.json` 损坏时按文件名排序全量重建并校验 `seq` 连续性。

### 15.3 延迟与吞吐目标

| 操作 | 目标 |
| --- | --- |
| 锁等待（session 锁 + gate 共享锁） | p99 ≤ 10 ms |
| 单事件 append（含 `fsync`，本地 SSD） | p99 ≤ 20 ms |
| 每次工具调用的日志开销（planned + started 两次 `fsync`） | p99 ≤ 40 ms，计入工具总耗时 |
| 上下文构造（≤ 200 事件，未压缩） | p99 ≤ 150 ms |
| compaction（含模型调用） | p95 ≤ 8 s，异常不阻塞当前 turn 超过 1 次重试 |
| 跨会话检索（90 天窗口，有索引） | p95 ≤ 800 ms |
| 跨会话检索（索引缺失全量扫描） | p95 ≤ 5 s，并上报降级 |
| 单 session 追加吞吐 | ≥ 50 事件/s |
| 单主机追加吞吐 | ≥ 500 事件/s |

`started` 事件使每次工具调用和每次投递各多一次 `fsync`。这是为换取「已规划 / 已发起」可判定性而主动付出的成本：相对工具与投递本身的网络耗时（通常数百 ms 起），两次本地 `fsync` 可忽略，且**不得**通过合并事件或省略 `fsync` 来优化（§8.1 第 3 条）。

超出目标 2 倍持续 5 分钟即触发告警。

## 16. 迁移、切换、恢复与回滚

### 16.1 切换步骤

采用干净切换，不做旧记忆双读双写：

1. 停止入口并等待旧任务结束，导出旧会话供人工审计（导出为只读归档，不进入新日志）。
2. 初始化新的本地事件目录、权限、身份 salt 和备份策略，运行启动自检（§6.1）、恢复演练和崩溃注入测试（§19.2）。
3. 在隔离流量验证事件回放、工具对账和投递计划扫描，跑通全部 §19 验收。
4. 切换入口，新版本只写本地 append-only 日志，不导入旧摘要。
5. 接受第一条新流量后，禁止回退到旧存储。故障时关闭入口、保留新事件并向前修复。
6. 验证稳定后删除旧写入代码和 feature flag；`analysis_snapshots` 与交易表因属于业务事实继续保留。

### 16.2 回滚边界

**不可逆点 = 新存储中第一条 `user/message` 完成 `fsync` 的时刻。**

- 该时刻之前（步骤 1–3）：可整体回滚，删除新目录即可，旧链路未受影响。
- 该时刻之后：禁止回退到旧存储，禁止把新事件反向写入旧格式。允许的处置只有：关闭入口止损 → 修复代码 → 重新开放入口 → 必要时按 §19.1 重建全部派生投影。
- 任何“临时双写回旧存储”的方案一律禁止，包括应急场景。

### 16.3 版本切换

事件格式变更采用“读取器先兼容、再写新版本”，两者之间至少间隔一次完整发布并完成灰度观察。未知核心事件 fail closed，避免旧版本静默忽略新语义。降级发布前必须确认新版本尚未写入任何当前运行版本无法读取的 `format_version` 或核心 `schema_version`；已写入则不允许降级。

### 16.4 未来水平扩容

先保持 `SessionStore` 接口和事件协议不变，再整体替换权威存储或引入单 session owner；不得用本地日志与 PostgreSQL 双写来过渡。当前架构不为尚未发生的扩容增加数据库依赖。

### 16.5 旧机制退役顺序

P9 已按以下顺序完成且不保留兼容开关：移除 `build_light_agent_input()` 摘要首屏 → 从工具注册表移除 `get_last_snapshot` / `search_conversation_summaries` → 停止写 `turn_summary` 与 `recent_message` → 移除 `last_snapshot` 状态字段 → 删除旧 JSON 会话持久化实现。`scripts/guard_no_legacy_memory_path.py` 阻止这些模块和调用重新进入运行路径。

### 16.6 恢复演练

每季度至少一次，在非生产环境执行并记录结果：从备份恢复 session 分区与 blob → 校验全部 `record_checksum` → 重建 head 投影与幂等索引 → 比对恢复前后 `(active_branch_id, branch_heads, last_seq)` 与全部 `(scope,key)` 集合完全一致 → 抽样复现 3 条历史 `model/request` 的逐字请求体。

## 17. 失败模式与恢复

| 失败 | 处理 |
| --- | --- |
| 本地日志 `write` 失败 | 在锁内回退到写前 offset 并 `fsync`；本轮未被接受 |
| `fsync` 失败 | 提交状态不确定，立即将 store 标为不可写；不执行外部副作用，重新打开并恢复后以同一幂等键重试 |
| 锁等待超时 | 退避重试 3 次后返回 `StoreBusy`；用户侧提示重试，不丢消息 |
| 删除意向标记存在 | append 立即返回 `StoreBusy`，让在途写入有界排空，不与 gate 争抢 |
| scope 目录已被删除 | append 返回 `SessionErased`，不重建目录，不复活数据 |
| 删除 gate 获取超时 | 释放 gate、删除 intent 标记并告警，删除任务稍后重试；步骤可重入，不留半删除状态 |
| 父节点冲突 | 返回 `ParentConflict`；上层重读后重试或建分支 |
| PostgreSQL 业务库不可用 | 普通对话继续；依赖它的交易、持仓或快照工具返回明确失败并形成完整 call/result |
| 模型流式输出中退出 | 追加或保留 `assistant/attempt`；无已提交 call 时可重试，上限 3 次后 `turn/aborted` |
| assistant 已提交、planned 写入前退出 | 从 assistant tool call 补写 planned，再进入正常恢复流程 |
| planned 已提交、started 写入前退出 | 外部调用确定未发起：继续执行或追加 `interrupted`，对 `opaque_effect` 同样安全 |
| started 已提交、外部调用前退出 | 结果不确定：按事件中固化的 `effect_class` 对账，禁止盲目重放 |
| 工具成功、结果写入前退出 | 同上按 `effect_class` 对账；`opaque_effect` 记 `unknown` 转人工 |
| 工具 call 永久无结果 | 自动追加 `interrupted`（无 started）或 `unknown`（有 started），保证上下文协议完整 |
| `unknown` 后续可对账 | 追加 `tool/reconciliation`，投影覆盖原状态 |
| 注册表 `effect_class` 与事件固化值不一致 | 以事件固化值为准，只允许向更保守方向升级并上报漂移指标 |
| delivery/planned 已提交、started 写入前退出 | 尚未发送，worker 可安全发送 |
| delivery/started 已提交、结果写入前退出 | 可能已送达：可对账则对账；不可对账则停留 `unknown`，默认不自动重发 |
| 飞书发送超时 | 记 `unknown`，先对账；不支持对账时不自动重复发送 |
| 重复 webhook | 幂等键命中返回已有处理结果，不追加用户事件 |
| 并发写同一分支 | OS 文件锁串行化；父节点不匹配则冲突重读 |
| 尾行半写或尾行 checksum 错 | 持锁截断至最后有效 offset，追加独立 `tail_truncated` 运维审计记录 |
| 中部 checksum 错或 seq 跳跃 | fail closed，session 隔离并报警，从备份恢复 |
| blob 缺失但未过期 | 按 `raw_content_unavailable` 投影并告警，不删除事件 |
| blob hash 不匹配 | 视为数据不完整，按缺失处理并告警 |
| 磁盘空间低于 `min_free_bytes` | 拒绝新 blob 与新 turn，保留已接受事件，立即告警 |
| checkpoint 不完整 | 不提交，使用旧 checkpoint 或抽取式 fallback |
| 单工具结果超过窗口 | blob 保存原文，模型只读有界投影 |
| 压缩后仍超限 | 减少完整 turn、分层压缩、抽取 fallback；仍超限 `turn/aborted(context_overflow)` |
| 历史搜索无证据 | 一次修复后降级为证据不足 |
| 检索索引不可用 | 退化为全量扫描并上报降级，不返回空结果 |
| 未知核心 schema / 过高 format_version | fail closed 并报警，不构造残缺上下文 |
| 索引或 head 投影损坏 | 从事件日志重建，不影响权威数据 |
| 时钟回退 | 照实记录并上报；时间窗查询按 `max_clock_skew` 容差处理 |

## 19. 验收与测试矩阵

全部条目为可执行测试。崩溃注入通过环境变量 `CONTEXT_CRASH_POINT=<point>` 在指定位置使进程 `_exit(1)`，注入点固定为以下 14 个：

```text
before_blob_rename                      after_blob_rename
before_append_write                     after_append_write_before_fsync
after_fsync_before_index
after_planned_before_started            after_started_before_tool_execute
after_tool_execute_before_result
after_delivery_planned_before_started   after_delivery_started_before_send
after_delivery_send_before_result
before_compaction_commit
before_erase_rename                     after_erase_rename_before_cleanup
```

### 19.1 回放、分支与投影

- 任意已完成 turn 可恢复用户消息、精确模型请求、响应、工具调用和结果。
- 两个进程并发对同一 parent 追加时只有一个成功，另一个收到 `ParentConflict`，文件中不出现双 head。
- 32 进程 × 100 次并发追加后：`seq` 连续无空洞无重复，事件总数等于成功返回数，无 checksum 失败。
- 创建多个叶子后只回放最新 `branch/activated` 指定分支。
- 删除 head 投影与幂等索引快照后，仅从事件重建出相同 `active_branch_id`、`branch_heads`、`last_seq` 与 `(scope,key)` 集合。
- 分区轮转后 `seq` 跨分区连续；删除 `parts.json` 可重建且校验通过。

### 19.2 幂等与崩溃注入

- 同一 webhook 投递两次只产生一个 `user/message` 和一次 Agent Loop；第二次返回 `deduplicated=true`。
- 同一 assistant event 重复调度投递只产生一个 delivery key；超时路径不虚报成功。
- 在上述 14 个注入点各崩溃 100 次并重启恢复后：无孤立 `tool/call_planned`、无重复副作用、无中部损坏、事件集合满足全部 §5.2 不变量。
- `after_append_write_before_fsync` 注入产生的尾部残行必须被自动截断并追加独立运维审计记录；随后追加可正常进行。
- 人为改写文件中部一个字节后，启动必须 fail closed 并隔离 session，不得跳过继续回放。
- **`after_planned_before_started`**：恢复后日志中该 call 无任何 `tool/call_started`；对全部四类 `effect_class` 均判定为「未发起」，或继续执行（先补 started）或落 `interrupted`；外部系统**零调用**。以 `opaque_effect` 模拟下单工具重复该用例 100 次，外部台账始终 0 条记录。
- **`after_started_before_tool_execute`**：恢复后一律判定为「结果不确定」，`opaque_effect` 必须落 `unknown` 且外部零重试；`queryable_effect` 只发查询请求、不发执行请求（以 mock 断言请求类型）。
- **`after_tool_execute_before_result`**：通过相同 `operation_id` 对账且不重复下单；外部台账恰好 1 条。
- `pure_query` 的重放路径同样必须先写 `tool/call_started`；断言每次外部调用前日志中都有对应 `attempt_no` 的 started（started 计数 ≥ 外部调用计数）。
- **`after_delivery_planned_before_started`**：恢复后可安全发送，用户恰好收到 1 条。
- **`after_delivery_started_before_send`** 与 **`after_delivery_send_before_result`**：不可对账的供应商下默认不自动重发，结果停留 `unknown`；可对账的供应商下先查后补，用户不会收到第二条。
- `effect_class` 漂移测试：写入 `opaque_effect` 的 planned 后，把注册表改为 `pure_query` 再崩溃恢复 —— 恢复必须仍按事件固化的 `opaque_effect` 处置，外部零重放，并上报 `context_effect_class_drift_total`；反向（注册表更保守）时按更保守值处置。
- 孤立 `tool/call_planned` 在进入模型上下文前一定得到 `interrupted`、`unknown` 或对账结果。
- `tool/call_started` 与 `delivery/started` 不出现在任何 `model/request` 的请求体中（逐字断言）。
- 删除 PostgreSQL DSN 或停止数据库后，普通聊天、历史检索和 compaction 仍能运行；数据库业务工具返回明确错误并形成完整 call/result。

### 19.3 锁与删除并发

- 32 进程持续 append 同一 scope 的 8 个 session，同时发起一次 scope 删除：删除在 30 s 内取得 gate（intent 标记生效），全程无死锁、无进程挂起；删除后所有 append 返回 `StoreBusy` 或 `SessionErased`，无一成功写入。
- 删除进程与 append 进程的锁序断言：注入检测器验证任一进程从不同时持有两把 session 锁，且从不在持有 session 锁时申请 gate。
- **`before_erase_rename`** 崩溃：用户数据完整可用，intent 标记被清理或超时释放，后续 append 恢复正常。
- **`after_erase_rename_before_cleanup`** 崩溃：用户数据已不可检索；重跑删除从清理步骤继续并最终完成，不出现半删除状态。
- `rename` 与 append 的竞态：在 `rename` 前一刻放行一个已通过路径校验的 append，断言它要么阻塞在 gate、要么写入已被移走的 inode 随隔离目录删除，**不重建 scope 目录**。
- 删除完成后同一 scope 新建 session：必须显式创建 `session/header` 且校验删除墓碑，不得由 append 隐式重建目录。

### 19.4 上下文与压缩

- 最近 turn 以原文进入上下文，工具调用与结果不被切开。
- 历史 `model/request` 始终引用原 checkpoint，追加新 checkpoint 后重放历史请求字节完全一致。
- 单个超大工具输出只将有界投影送入模型，原始 blob 可审计且 hash 可校验。
- checkpoint 加近期原文仍超限时按 §10.2 顺序降载；不提交截断摘要；最终超限返回 `turn/aborted(context_overflow)` 而非静默丢弃。
- `before_compaction_commit` 崩溃后日志中不存在半成品 checkpoint。
- 装载断言测试：人为构造孤立 tool call、越界 `first_kept_event_id`、未知核心 schema，均拒绝构造上下文。

### 19.5 跨会话检索与 ETH 回归

对“最近一周我是不是一直让你找多头机会”建立至少两个 session 的测试数据：

- 召回时间范围内全部相关用户原话及对应助手回复。
- 区分“用户持续要求找多”“助手给过条件计划”“条件是否触发”“是否实际建单”。
- 次数和持续性结论带有效事件引用与 `retrieval_receipt`；缺少逐根历史行情时不推断条件已触发。
- 移除一项证据后触发一次补查；仍不足则输出证据不足，不假回忆。
- 引用伪造测试：草稿中写入不存在的 `event_id`、他人 `event_id`、未装载 `event_id`、仅 `checkpoint_cited` 的 `event_id`，四种情况全部被拦截。
- `truncated=true` 的检索结果不得支撑“共 N 次”“从未”类结论。
- 模型工具参数中传入其他 `visibility_scope_id` 时被忽略并计数告警。

### 19.6 schema、留存与恢复

- 未知 `aux` 事件可保留并跳过；未知 `core` 事件阻止上下文构造；`format_version` 过高无条件 fail closed。
- blob 到期后保留 hash 和投影并标记原文不可用；删除 tombstone 后读取行为不变。
- scope 删除后事件、索引和无共享引用 blob 均不可检索；仍被其他 scope 引用的共享 blob 保留。
- blob GC 在 mark 阶段并发写入新 blob 时不误删（grace 生效）。
- 从备份恢复后的幂等键集合和分支推导结果与恢复前完全一致（§16.6 演练脚本化）。

### 19.7 容量、延迟与指标

- 20 万事件 session 的冷启动重建、上下文构造和检索延迟满足 §15.3 目标。
- 持续 1 小时 50 事件/s 写入无 `fsync` 失败、无锁饥饿、p99 达标。
- 磁盘空间低于 `min_free_bytes` 时拒绝新写入并告警，已接受事件不受影响。
- §15.4 全部指标可被采集；抽样断言指标与日志中不含用户原文。

## 20. 最终边界

这套方案不把人的观点预先编码成越来越多的状态字段。它保存经历本身，在需要时按当前问题重新取证，并要求回忆能够回到原文验证。

- 行情工具负责当前市场事实。
- 业务仓库负责订单、持仓和历史行情快照。
- 会话事件日志负责过去真实发生过什么。
- LLM 负责解释证据，不负责制造记忆。
