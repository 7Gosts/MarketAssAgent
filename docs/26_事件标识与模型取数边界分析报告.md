# 事件标识与模型取数边界分析报告

日期：2026-11-04

性质：基于当前项目代码的可行性分析，不是施工方案。本次只新增报告，没有修改程序、数据库或服务进程。工作区已有的上轮代码改动未在本次调整。

实施决策补记（2026-11-04）：用户随后明确选择移除存储中的事件哈希，而非只做模型输入投影。当前实现以数据库自增 `id` 和会话内 `seq` 取代 `evt_...` / `ev_...`，将历史数据迁至新格式，并删除旧历史工具结果中的嵌套轨迹。下文“保留当前存储身份”和“暂不迁移”是实施前分析结论，已由该决定取代；内容保留为决策背景。

## 一、结论

你的核心判断成立：**给 LLM 的数据应按业务需要选择，不应把数据库内部事件 ID 一并交给模型，再主要依赖模型生成后的清理。**

但有三个不同层次，需要分别判断：

| 主张 | 可行性 | 判断 |
| --- | --- | --- |
| 查询订单历史时不选择事件哈希字段 | 可直接实施 | 对 PostgreSQL 账本可以使用明确的列投影，改动很小 |
| 模型只看到时间和发生的事实 | 可实施 | 多订单查询还需要区分订单；交易事实还需要实际价格、数量等必要信息 |
| 用简单编号替代复杂事件哈希 | 可实施 | 哈希格式不是必须，整数主键或会话内序号也能承担事件身份 |
| 存储中完全取消事件标识，仅保留时间和内容 | 不适合当前系统 | 不能可靠区分重复投递与真实重复事件，也无法维持现有事件关联 |

最适合当前小程序的方向是：**先从取数接口排除内部标识；存储继续保留必要身份和去重规则。订单账本的额外哈希可以独立评估是否删除，会话日志不应因展示问题而整体迁移。**

## 二、当前项目并非所有取数都经过 SQL

项目有两套不同的事件存储。

| 数据 | 存储方式 | 标识 | 当前读取入口 |
| --- | --- | --- | --- |
| 模拟订单创建、成交、止损、止盈 | PostgreSQL 的 `journal_events` 表 | `evt_...`，另有自增主键 `id` | `PaperTradingRepository.list_recent_events()` |
| 用户消息、模型请求、工具调用、回复投递、压缩检查点 | 本地 JSONL 事件日志 | `ev_...`，另有会话内序号 `seq` | `LocalSessionEventStore.scan_scope()` / `read_branch()` |

因此：

- 对此前 SOL 订单中的 `evt_1561...`，你说的 `SELECT ... FROM ...` 完全适用。
- 对这次回复中的 `ev_55b795...`，实际读取的是 JSONL 日志，不存在相应的 SQL `SELECT`。等价的正确做法是：构造历史记录返回值时，只选文本、时间和必要业务事实。

SQL 和 JSONL 的实现不同，但模型输入的原则一致：存储元数据和业务事实应分开。

## 三、订单账本可以直接缩小 SELECT 范围

当前仓储使用：

```python
self.session.query(JournalEvent)
```

这会读取整个 ORM 实体，并不是只读调用方最终使用的几个属性。本次用 SQLAlchemy 的 PostgreSQL 方言编译确认，选择列包括 `id`、`event_id`、订单关联、状态变化、价格、请求 ID 和完整 `payload_json` 等字段。

如果用途只是向模型提供订单事件，查询可以表达为：

```sql
SELECT order_id, event_time, event_type, event_price
FROM journal_events
WHERE session_id = :session_id
ORDER BY event_time DESC, id DESC
LIMIT :limit;
```

这段 SQL 是建议示例，尚未实施。查询具体订单时，也可以加入已由服务端校验的 `order_id` 条件。

这里有两点：

1. `id` 可以只用于排序，不必出现在返回列或模型输入中。
2. 不选择 `event_id` 不意味着删掉数据库中的 `event_id`；读取接口与持久化表的职责不同。

这比“读取完整对象，再把事件哈希拼到工具结果里，最后清理”更直接。对于明确的只读展示用途，也不必为了复用 ORM 实体而增加通用映射框架。

已有的历史工具结果可能包含旧字段；旧数据重放时的窄范围过滤属于迁移兜底，不应替代新查询的列选择。

## 四、“时间和发生什么”应包含哪些业务事实

如果已经确定只查询一笔订单，模型通常只需：

- 事件发生时间。
- 事件类型，例如创建挂单、成交、止盈平仓、止损平仓、取消。
- 对应事件的实际价格，以及有记录时的实际数量和必要原因。

如果一次返回多笔订单，还需提供订单标识或明确分组，否则模型不能知道哪条成交、哪条止盈属于同一笔单。

你举的 `E0004` 是合理的业务展示编号，但当前项目实际使用 `ord_...`。是否新增简短订单编号是另一项需求，不能在删事件字段时顺带扩建。

交易复盘还应区分：计划入场价、实际成交价、计划止盈价、实际平仓价。仅有“某时发生了止盈”不足以计算净收益；手续费、滑点、资金费和中途仓位变化没有记录时，应明确缺失。

对话历史则需要时间、说话角色和原文。业务对象已经清楚时，内部消息 ID 没有必要让模型看到。

## 五、事件身份、哈希格式和内容校验不是一回事

| 概念 | 用途 | 是否必须是复杂哈希 |
| --- | --- | --- |
| 事件身份 | 精确指出一条记录，供关联或定位使用 | 否，可以是整数或复合键 |
| 幂等键 | 判断同一次操作重试是否已经处理 | 否，可以是业务唯一约束或外部消息编号 |
| 事件顺序 | 区分先后关系 | 否，通常使用序号 |
| 内容校验哈希 | 检查内容是否损坏或变化 | 与事件 ID 独立，应另行评估 |

当前 `evt_...` 基于业务参数生成截取的 MD5；`ev_...` 基于会话和幂等参数生成截取的 SHA-256。它们都不是密码，也不是因为“AI 更专业”而需要的格式。

会话日志另外有 `record_checksum`，大内容存储另外有内容哈希。**删除事件哈希字段，不等于可以同时删除日志校验和 blob 内容哈希。**

所以，“这串哈希没必要存在”作为格式判断有讨论空间；“记录不需要任何身份”则是不同且更强的判断。

## 六、为什么时间和内容不能直接替代所有事件标识

时间不是可靠的唯一键：

1. 同一根 K 线可能同时导致挂单成交与止盈/止损判断，两个事件可以使用同一根 K 线的时间。
2. 两笔订单可能同时成交，事件类型、时间和价格都相同。
3. 同一条飞书消息可能重复投递；也可能是用户真的连续发送了两条相同内容的消息。仅比较时间和内容不能可靠区分。
4. 一次网络或进程故障后，需要判断某次工具操作是否执行、某条回复是否已经发送。应关联具体操作，不能靠“时间大致相近”猜测。

自增主键可以区分记录，但单独使用自增主键不能阻止同一操作重复插入；每次重复插入都会得到新的数字。

因此，保留简单内部身份与业务去重规则是合理的。模型不需要知道这些身份，不代表程序不需要。

## 七、订单事件的额外哈希确实有简化空间

`JournalEvent` 已经有自增主键 `id`，`event_id` 是另一个带唯一索引的字符串键。

当前运行代码中，订单读取与操作主要通过 `order_id`；没有发现以 `evt_...` 为必需参数的业务操作入口。事件哈希的直接作用主要是写入唯一约束和内部/工具结果展示。

因此，删除订单事件的额外哈希字段在技术上可行。例如可以保留：

```text
id：数据库内部主键
order_id：事件属于哪笔订单
event_time / event_type / event_price：业务事实
业务唯一约束：防止同一状态变化重复记录
```

当前状态流转哈希由 `order_id + event_type + event_time` 生成。若确认现有业务保证同一订单在同一时间最多发生一次同类型事件，就可以评估直接使用这些列的唯一约束，而不再生成独立哈希。

需要核实的条件是：

- 将来或现有流程是否允许同一时间多次部分成交、部分平仓或调整；若允许，上述复合键可能把合法事件当重复。
- 创建事件重试时，时间会重新生成；不能只用“新时间”做创建去重，仍需依赖已有请求身份、订单唯一性或独立业务去重条件。
- 当前代码先校验旧状态，再写入事件，并对 `IntegrityError` 回滚。唯一键不是整个状态机幂等性的唯一保证；换键后需复核状态检查和异常处理。
- 删除字段涉及表和索引迁移、写入函数、读取结果及部署顺序，不能直接删一行模型字段后宣布完成。

这是一项可以单独做的小型存储简化，不需要新的 ID 服务或通用事件框架。本次未进行重复数据审计或并发验证，以上属于有条件可行。

## 八、会话事件哈希可替换，但不是局部删字段

会话日志没有 PostgreSQL 自增主键，但已有会话内 `seq`。理论上可以使用 `(session_id, seq)` 作为内部身份，以 `parent_seq` 等简单引用替代长哈希。

这个方向可行，但当前 `ev_...` 已承担实际关联：

- `parent_event_id` 和分支头记录父子关系。
- 工具计划/结果关联到具体助手消息与操作。
- 回复投递关联到具体回复，帮助避免重复发送。
- 压缩检查点记录覆盖区间与保留边界。
- 日志恢复和一致性校验通过事件 ID 解析这些关联。

去掉哈希后，上述关联仍要存在，只是改用另一种键。还需要保留独立的幂等判断，因为重试操作不能仅靠新分配的序号去重。

既有 JSONL、分支索引、检查点和事件格式验证都依赖当前 ID 形式。替换身份需要版本化迁移及恢复验证，不能通过修改一个 SELECT 或过滤字段完成。

历史 `model/request` 中保存的实际 API 请求也不应为了“消除旧 ID”而重写。新模型输入可以投影或清理旧数据；已经发出的历史请求应保持可复现。

对当前小程序，取消会话事件的哈希格式可能改善可读性，但不会自然减少关联逻辑。为解决模型回复暴露 ID 而启动整个会话存储迁移，收益不足。

## 九、对当前修复草稿的评价

当前工作区的上轮草稿已让历史检索结果不再给模型提供事件 ID，也不再要求模型生成 `[mem:...]`。这解决的是模型输入和回复边界。

但订单仓储仍使用 `query(JournalEvent)` 读取完整行，`get_journal_status()` 的原始结果仍曾组装 `event_id`，随后在协议投影中删除。**这不等于已经落实了你要求的 SQL 列选择。**

另外，取消引用后把历史校验改成仅检查检索回执，是独立的行为变化：

- 原校验不证明句子被原文语义支持，但能检查模型所指事件是否在已装载证据集合内。
- 回执校验检查本轮是否检索过、窗口是否覆盖、结果是否完整；不再保留逐句到事件的绑定。

两者不能表述为完全等价。仅仅不向模型提供数据库字段，并不自动要求取消或降低历史校验机制；这个取舍应独立决定。

## 十、建议的最小决策顺序

1. **先限定模型读取契约。** 订单复盘只查询必要业务列；对话历史只返回时间、角色、原文和必要工具事实。内部事件标识不进入这些返回值。
2. **保留当前存储身份。** 不因展示需求顺带迁移 JSONL，不把订单字段投影扩展成全项目 ID 改造。
3. **单独评估订单额外哈希。** 以已有 `id` 为内部主键，核实业务唯一约束是否可以替代 `evt_...`。规则成立再做独立迁移。
4. **独立决定历史校验强度。** 若只要检索过程约束，回执检查较简单；若要逐句来源定位，就必须有一种引用关系。两者都不能代替语义核验。

这条顺序让“模型不要看到复杂 ID”先用小改动完成，而是否删除存储哈希由真实用途决定。

## 十一、验证与性能预期

本次做了代码调用链核对，以及不连接数据库的 SQLAlchemy SQL 编译；没有执行数据库迁移、写入、服务重启或代码修改。

未来验证应围绕业务行为：查询结果不包含事件 ID；同时间的不同订单不会混淆；重试不重复写单或状态事件；历史读取仍区分角色和时间；旧日志能恢复、工具和投递仍正确关联。

缩小 SELECT 列不会改变查询过滤和排序的渐进复杂度，但会减少每行传输和 ORM 对象装载的数据量，尤其能避免读取不需要的 `payload_json`。实际速度收益取决于数据大小、索引和数据库 I/O；本次未做基准测试，不声称一定明显提速。

JSONL 读取是本地日志扫描，输出字段减少主要改善模型输入大小；不能把它描述为 SQL 查询优化，也不会仅靠隐藏 ID 消除扫描成本。
