# 可信行情分析报告

**调研日期**: 2026-10-15

**状态**: 调研与设计建议；当前实施状态见 [25_可信行情分析优化方案.md](25_可信行情分析优化方案.md)
**目标**: 让 MarketAssAgent 的行情分析更可证伪、更少事后合理化，并把 LLM 的叙事能力约束在证据和可回放流程里。

---

## 1. 结论

技术分析应被当作概率系统，而不是每次预测行情的神谕。一个分析方法只需要在足够样本、固定规则和可复现实验下体现正期望；单次判断可以错，关键位可以失效，模型可以被行情打脸。可信系统要记录失败，而不是用后续行情倒推一个“其实当时也对”的解释。

LLM 的问题不是“不懂交易”这么简单，而是它天然擅长生成连贯解释。在没有证据边界、时间隔离和评分规则时，它很容易把结果写成一篇看似公正、实则自圆其说的文章。因此，本项目后续不应只靠提示词要求“客观”，而要把行情事实、历史原文、预测快照、复盘评分和最终表达分层编排。

最小改进方向是：普通行情分析继续轻量；当用户要求“复盘、验证、过去判断是否有效”时，进入可信复盘模式，只评价当时真实说过的计划，只使用截止当时可见的数据重建背景，再用后续行情按固定规则打分。旧判断错了就记错，新行情产生的新解释另算。

## 2. 外部调研要点

### 2.1 交易与回测侧

交易社区和量化工具的共同经验是：不能让未来数据进入当时的决策，也不能用事后挑选的样本证明策略有效。Freqtrade 的 `lookahead-analysis` 会专门检查回测中是否使用了未来信息；QuantConnect 文档也反复强调 walk-forward / out-of-sample 这类验证方式，用来降低过拟合和样本内自嗨。

对本项目的启发：

- “只看某个截止时点前的 K 线”必须是代码层过滤，而不是让 LLM 口头承诺。
- 关键位是否有效，要先冻结关键位、触发条件、失效条件、有效期和评分口径，再看后续行情。
- 如果价格跌破支撑，不能自动把它解释为“支撑转压力所以支撑有效”；除非当时计划里明确写了“跌破后反抽该位受阻才算二次验证”。
- 胜率、盈亏比、最大回撤、样本量、交易成本和滑点，要比单次“点位命中”更重要。

### 2.2 LLM 与 agent harness 侧

OpenAI 关于幻觉的分析指出，模型在常规评测和问答压力下会倾向猜测；如果错误回答和承认不知道的惩罚结构不合理，模型会更愿意给出看似完整的答案。LangSmith / AgentEvals 这类 agent 评估工具强调的也不是“提示词写得更严厉”，而是对工具轨迹、最终回答和任务结果做可重复评估。

DeepSeek API、OpenAI Agents SDK、LangGraph / LangSmith、Pydantic AI 等生态里的经验大体一致：

- 工具调用要留下轨迹，便于复现模型当时看到了什么。
- 结构化输出和 schema 能降低格式漂移，但不能证明语义真实。
- RAG 或历史检索要返回证据，而不是只返回摘要。
- 对 agent 要做 trajectory / tool-use 评估：该查历史时是否查了，该用工具时是否用了，有没有越权使用未来信息。
- 人工或模型裁判可以辅助评估，但关键约束要尽量确定性化，比如时间窗、事件引用、快照 ID、价格序列截止点。

对本项目的启发：

- 仅在 `core/prompt.py` 里追加“不要事后诸葛”不够。提示词可以约束表达，但无法保证模型没有看过未来数据。
- 复盘类任务需要独立的输入包：历史原文、当时快照、后续行情、评分规则分别进入不同阶段。
- LLM 可以负责解释和总结，但“是否看到了未来”“当时是否真的说过”“规则是否触发”这些判断应尽量由代码或结构化证据承担。

## 3. 本项目现状

### 3.1 已经做对的部分

项目已经有一些不错的底座：

- `LocalSessionEventStore` 保存用户消息、模型请求、工具调用和回复事件，是对话历史的真相源。
- `model/request` 会记录模型当时收到的上下文，理论上可以审计某次回答是否已经包含了未来行情。
- `search_session_history` 能从原始事件里找用户和助手当时的原话。
- `HistoricalClaimGuard` 要求“之前、一直、多次、从未”这类历史对话主张带事件引用，证据不足时会降级。
- `analyze_market` 输出 `market_facts.v1`，把均线、结构、关键位、量价等事实与 LLM 的交易判断分开。
- `analysis_snapshots` 已经保存每次分析的轻量快照，后续可作为“当时分析结果”的业务证据。
- 用户画像里的 `advice` 可以提醒模型在用户连续亏损、情绪上头或违反纪律时更具体地提示，而不是泛泛喊风险。

这些能力说明项目已经不是纯 prompt bot；它已经具备“可取证、可回放、可落库”的基础。

### 3.2 当前暴露的问题

最近这次 ETH 复盘暴露的问题主要不在行情工具本身，而在复盘任务的编排边界：

- 所谓“盲测”并不是真盲测。模型拿到了完整后续 K 线和前一段事后复盘，然后在同一轮里写“截止某时点的计划”和“揭开后续走势”。
- 评分口径不可证伪。支撑守住可以说有效，支撑跌破又可以说“跌破后转压力也有效”，这样会让技术分析永远显得正确。
- 原始建议与后续复盘混在一起。后来的模型不能把新的确认条件倒灌回旧建议里，再用它评价用户是否执行偏离。
- `level_zones_v1.touches` 当前是候选点簇数量，混合了分形、近 12 根高低点和斐波那契价位，不等于真实独立触碰次数。LLM 如果把它写成“多次触碰验证”，就会夸大证据。
- `HistoricalClaimGuard` 目前校验的是历史引用是否存在、是否完整，不校验“这句话是否真的由引用推出”。它能防一部分编造历史，但不能防语义偷换。
- 当前行情工具偏“现在怎么看”，缺少“给定截止时间，只用当时之前的数据重算”的正式 replay 能力。

## 4. 可信分析原则

### 4.1 技术分析的可信边界

技术分析输出应明确区分四类话：

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 事实 | 工具直接给出的行情状态 | “ETH 4h 收盘价在 55MA 下方” |
| 推断 | 基于事实的概率判断 | “空头延续概率更高” |
| 计划 | 可执行、可失效的条件 | “反抽 2508-2527 受阻才空，收上 2538 失效” |
| 复盘 | 后续行情对旧计划的评分 | “未触发 / 触发后止损 / 触发后达一倍风险收益” |

不能把复盘里的新事实改写成当时的推断，也不能把推断失败解释成“其实关键位还是有效”。

### 4.2 允许失败

可信分析必须允许出现这些结论：

- “这次方向判断错了。”
- “关键位有反应，但交易计划不赚钱。”
- “价格碰到区间，但没有出现当时要求的确认，所以不算触发。”
- “方向最终对，但先打止损，所以这笔交易仍算失败。”
- “样本太少，不能证明方法有效。”

如果系统不能自然说出这些话，它就会滑向事后完美幻觉。

### 4.3 评分要拆开

复盘不要只写“支撑/阻力有效吗”，而要拆成独立评分项：

| 评分项 | 判定方式 |
| --- | --- |
| 关键位反应 | 后续 N 根 K 线内是否在预设距离内出现反应 |
| 方向判断 | 到期时价格是否沿预期方向运行 |
| 触发条件 | 是否满足当时写下的入场确认 |
| 失效条件 | 是否先触发止损/失效线 |
| 交易结果 | 按固定入场、止损、止盈、费用和滑点计算 R 倍数 |
| 表达质量 | 当时有没有写清条件、有效期、风险和不确定性 |

这样可以接受“位对、交易错”“方向对、计划亏”“计划没触发、不能算赢”等更真实的结果。

## 5. LLM 编排建议

### 5.1 普通行情分析保持轻量

用户只是问“ETH 怎么看”时，不需要引入复杂 harness。当前链路可以继续：

```text
用户问题
  -> analyze_market / get_contract_sentiment / 持仓工具
  -> get_previous_analysis_snapshot
  -> LLM 给出结论、条件、失效、复核时间
```

但表达上应减少“确定性预测”，多使用概率语言：

- 用“更偏向、概率更高、需要确认、失效条件是”。
- 少用“必然、证明、完全命中、盘面验证了我”。
- 明确“这是当前结构下的交易假设，不是行情保证”。

### 5.2 复盘和验证进入可信复盘模式

用户问“之前分析有效吗”“是不是事后诸葛”“用后面走势验证”时，进入单独流程：

```text
1. 取证
   - search_session_history 找当时真实原文
   - analysis_snapshots 找当时保存的行情快照
   - model/request 审计当时模型可见输入

2. 冻结旧计划
   - 只抽取旧回复里明确写出的方向、入场区、止损、止盈、失效、有效期
   - 没写清的字段标记为 unknown，不由后续模型补写

3. 获取后续行情
   - 只取旧计划之后、评估窗口之内的 K 线
   - 固定费用、滑点和 intrabar 判定规则

4. 机械评分
   - 先判断是否触发
   - 再判断止损/止盈/到期结果
   - 分开给关键位、方向、交易结果、表达质量评分

5. LLM 总结
   - 只能解释评分结果
   - 必须保留失败项
   - 不允许新增旧计划没有写过的确认条件
```

这里的关键是：LLM 不再自己写“当时我会怎么计划”，而是评价“当时实际说了什么”。

### 5.3 真正历史 replay 另做

如果要做“在 2026-10-11 20:00，只看此前 K 线，让模型重新分析，再用后续验证”，那是另一类 replay 实验，不等同于复盘旧对话。

它需要：

- `fetch_market_data` 或 `analyze_market` 支持 `end_time` / `cutoff_time`。
- 所有指标、分形、斐波那契和多周期数据都在 cutoff 前过滤。
- 末根未收线 K 线要么剔除，要么明确标记。
- 模型请求中不得包含 cutoff 之后的原文、摘要、快照或工具结果。
- 先保存冻结预测，再由另一个阶段读取后续行情评分。

这类 replay 能验证“方法在历史时点是否有前视价值”，但不能替代对真实历史回复的审计。

## 6. 分阶段改进建议

### P0：先改表达边界

不急着加复杂系统，先把复盘回答的口径收紧：

- 禁止把“支撑跌破”直接算作支撑有效，除非旧计划预先定义了跌破后的 retest 评分。
- 禁止把后续才形成的确认条件倒灌回旧建议。
- 当样本只有一两次时，只说“个案支持/不支持”，不说“方法有效”。
- `touches` 对外表达为“候选点簇数量”或干脆不展示为触碰次数。

这部分可以通过少量 prompt 和展示层文案完成，但要承认 prompt 只能改善表达，不能保证实验隔离。

### P1：做可信复盘最小闭环

优先做一个只读复盘工具或内部服务，复用现有数据：

- 输入：`symbol`、`interval`、`start_time`、`end_time`、可选 `event_id`。
- 读取：会话原文事件、当时分析快照、后续 K 线。
- 输出：旧计划抽取结果、缺失字段、触发/止损/止盈/到期评分、证据引用。
- 失败模式：旧计划字段不完整时返回 `unverifiable`，不要让 LLM 补齐。

这一步不需要新数据库表，可以先把结果作为普通工具观察进入回复；真正需要长期统计时再考虑落库。

### P2：补历史 replay 能力

为行情工具增加可选 cutoff：

- `fetch_market_data(symbol, interval, end_time=...)`
- `analyze_market(symbol, interval, cutoff_time=...)`

实现重点不是参数本身，而是所有派生指标都必须基于 cutoff 后的数据切片计算。尤其是分形 pivot 需要右侧确认，不能在截止点附近偷看未来 K 线。

### P3：建立小样本 eval 集

从真实对话里挑选 20-50 个复盘样本，建立离线评估：

- 是否调用了历史检索。
- 是否只评价旧回复真实写出的条件。
- 是否承认失败和不可验证。
- 是否避免“方向最终对所以计划也对”的偷换。
- 是否输出固定评分表。

这比继续堆提示词更有价值，因为它能持续发现模型在不同版本、不同供应商下的叙事漂移。

## 7. 建议的目标状态

最终目标不是让机器人“预测更神”，而是让它成为一个诚实的交易分析工作台：

- 行情工具负责事实。
- LLM 负责把事实组织成交易假设。
- 历史事件负责证明当时说过什么。
- 快照负责证明当时看到了什么。
- 评分器负责证明后续是否触发、是否失败、是否盈利。
- LLM 最后再把这些结果讲清楚。

这种系统依然会错，但它的错误可见、可复盘、可改进。长期看，可信度来自“大样本下是否有正向胜率和正期望”，不是来自单次回答能不能把后续行情解释圆。
